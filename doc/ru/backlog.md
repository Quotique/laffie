### 2. PEG-грамматика: `a - 3^x` не парсится

`minus_number` съедает `- 3`, PEG не откатывается из успешной
альтернативы (packrat, упорядоченный выбор), и `^` дальше не
разбирается. Ошибка «expected one of ...» на ровном месте.

Воспроизведение: терм `x - 3^x` в любом .pbl / .sym.

Указатели: src/parser/grammar.rs:200–217 — альтернативы `sum()`
с `minus_number` (строки 204–207) стоят раньше общего вычитания
(строка 208) и не проверяют, что за числом не следует `^`.

Набросок: в альтернативах 204–207 добавить негативную опережающую
проверку `!"^"` после `number`, либо разбирать `- N ^ …` как
`-(N^…)`-вычитание (математическая конвенция: `-3^2 = -(3^2)`).
Конвертер импорта (scripts/iskra_import.py, `neg_ctx`) сейчас обходит
дыру скобками — после починки обход можно снять.

### 3. Given `x in Reals` для неизвестной = готовый ответ find(x)

Посылка «x вещественно» в виде given `x in Reals` немедленно
принимается решателем как разрешение цели `find(x)` — поиск
обрывается за ~17 циклов с ответом `x ∈ ℝ`.

Воспроизведение: задача `goal find(x); x in Reals; x^2 == 4;`.

Вопрос семантики: `in Reals` сейчас неотличим от ответа-множества
(`x in set(...)`). Нужен признак «тривиальное/несобственное
множество» (ответом считать только собственное сужение), либо
отдельный предикат вещественности вне answer-формы. Конвертер импорта
такие посылки не эмитит (см. iskra_import.py) — после починки можно
эмитить честно.

### 4. Wall-clock лимит проверяется раз в цикл — таймауты не срабатывают

`RunControl` сравнивает `deadline_at` на границе цикла
(src/solver/task/solver.rs:99), а раздувание термов внутри одного
цикла (например, нормализация `(2^(x+y))^(x^2-x*y-8)` из
`iskra:,:30`) блокирует решатель на минуты. В пилотном прогоне — 34
задачи упёрлись во внешний `timeout 60` при `-l 30`.

Воспроизведение:

```bash
cargo run --release --bin cli -- -c config/cli.yaml -p tasks/iskra --only "iskra:,:30" -l 5
# работает много дольше 5 секунд
```

Набросок: проверять дедлайн и в глубине — в нормализации/раскрытии
степеней (самые тяжёлые места), например через периодический опрос
CancelToken по счётчику узлов; и/или структурный предохранитель на
размер терма при раскрытии степеней с символьным показателем.

Уточнение 2026-09-27: шесть задач `eq_32`, висевших дольше внешнего
таймаута, стояли не в раздувании терма, а в калькуляторе `sympy_solve`
(общий `sympy.solve` на радикалах, см. §10); калькулятор ограничен
многочленами. Дедлайн внутри калькулятора питона не проверяется — та
же дыра для любого символа с `py`.

### 6. Goal-терм prove переписывается transform'ом до примерки правил — паттерны в «естественной» записи не матчатся

Симптом: `<=>`-правило с паттерном в естественной записи цели
(`3*(a*b + b*c + a*c) <= d`, `d <= (a + b + c)^2`) не срабатывает на
задаче `prove(3*(a*b + b*c + a*c) <= (a + b + c)^2)`, хотя паттерн
синтаксически идентичен цели.

Диагноз (по трассе `rule_selection`/`hypothesis`, config/cli_trace.yaml):
**матчер ни при чём** — goal-терм prove-задачи до примерки
Equivalence-правил переписывается transform-упрощением, раскрывающим
скобки: к моменту подбора правил цель уже
`3ab+3ac+3bc <= 2ab+2ac+2bc+a^2+b^2+c^2`, и паттерн в исходной записи
её не застаёт. `try_match`/`Rule::apply` на исходных формах проходят —
регрессионные тесты `nested_ternary_sum_*` в term/refer.rs и
rule/rule.rs фиксируют это.

Следствие для авторов правил: паттерн `<=>`-правила на цель писать в
ПОЛНОСТЬЮ раскрытой форме (обе части — плоские суммы), как SOS-факт в
lesser_or_equal.sym. Для `=>`-правил с goal-гейтом — наоборот,
goal-атрибут унифицируется с ИСХОДНОЙ (нераскрытой) целью, а резолюция
должна совпасть с раскрытым goal-термом: goal-attr в естественной
записи, резолюция в раскрытой (рецепт — inequalities.md §«Цель
переписывается transform'ом»).

**Вернуться к transform-подзадачам** (решение пользователя: учесть при
следующем заходе в эту область). Вопросы к проработке:

- примерять Equivalence-правила и к ИСХОДНОЙ форме цели (до
  transform-упрощения) либо хранить обе формы в goal_index — авторская
  запись правил станет естественной;
- какие ещё формы цель теряет по дороге (раскрытие скобок — не
  единственное переписывание), и детерминирован ли итоговый канон —
  сейчас авторы правил подбирают форму паттерна по трассе;
- взаимодействие с канонизацией goal-терма из этапа 2 ineq
  (normalize(max) в Solution::new — см. inequalities.md «Усмотрение
  ответа»): двойная канонизация (нормализация + transform) должна быть
  описана в одном месте;
- после обновления transform ВЕРНУТЬ обходные правила к канонической
  записи: SOS-факт в lesser_or_equal.sym сейчас записан в раскрытой
  форме `3ab+3bc+3ca <= 2ab+2bc+2ca+a^2+b^2+c^2` — вернуть к
  `3*(a*b + b*c + a*c) <= (a + b + c)^2` (пометка в комментарии
  правила).

Указатели: solver.rs `transform`/`mark_replaced` (упрощение цели),
`suggest_rules`; трасса `rule_selection`/`hypothesis`
(config/cli_trace.yaml) показывает, какую форму цели застают правила.

### 9. Параметры по умолчанию — как в Искре

Сейчас переменная `find`-задачи вправе войти в ответ, только если она
объявлена `v is known` (`Task::known_vars`, `src/solver/task/mod.rs`).
Необъявленный параметр считается ещё одной неизвестной: не решается даже
`a + x == 0`. Импорт из Искры поэтому дописывает `p is known` к каждому
параметру (`scripts/iskra_import.py`).

В Искре умолчание обратное (`book/chap3.tex`, цели «неизвестные» и
«известно»): ответ может зависеть от любой переменной, кроме неизвестных
цели. Цель `известно y₁…yₖ` сужает это до исходных данных — в ответ
входят только неизвестные и yᵢ, прочие переменные исключаются.

Набросок: известны все переменные постановки, кроме перечисленных в
`find(...)`; явные `v is known` при наличии — сужение до исходных данных,
как `известно`. Что решить:
- переменные, которые вводят правила (`as D`, свежие переменные замен), —
  не из постановки, известными быть не должны;
- обратная совместимость корпуса: `is known` есть в `tasks/test/known.pbl`,
  `known_chain.pbl`, `tasks/regress/parameter.pbl`,
  `tasks/sympy_comparison/parametric.pbl` — где он частичный, смысл сменится;
- после перехода убрать дописывание `is known` из импорта.


### 10. Гипотеза нормализуется до проверки требований

`Rule::apply` (`src/solver/rule/rule.rs`) для каждого сопоставления сразу
нормализует резолюцию, а требования проверяет позже — `is_refuted` в
`solve_impl`. Требование вида `b is known` решается синтаксически и часто
заведомо ложно (правила одной переменной на системах), но резолюция уже
построена и нормализована, с вызовом калькуляторов. Так `sympy_solve`
запускался на радикалах и вешал решатель — калькулятор ограничен
многочленами, но лишняя работа осталась.

Набросок: `apply` получает `TruthCtx`; сопоставление, у которого
требование без свободных параметров уже ложно, пропускается до построения
резолюции. Мерить на медленной группе «холостой перебор в системах»
(`арккосинус:31`, `нормусм:02`, `плюс:059`, `предел:71`, `смоператор:01`).
Трассировщик перестанет считать такие правила сработавшими.

## Прочее

### 7. Автоснятие двойного минуса — грамматика не принимает `--a`

Закрыто частично: имя `subtree` убрано из `src/parser/rule.rs` (варианта
`RuleAttr::Subtree` нет, и ветка могла только паниковать на
`from_str().unwrap()`), вместе с фикстурой `subtree_rule()` и двумя
`#[ignore]`-тестами, которые её звали. Теперь `attr subtree` в `.sym` даёт
обычную ошибку загрузки «unknown attribute».

Осталось то, ради чего те тесты писались: правило `--a <=> a` **не
парсится** — PEG спотыкается на двойном минусе (`expected: one of "(",
"..", ...`), то есть `#[ignore]` скрывал не поведение движка, а дыру в
грамматике. Когда грамматика научится `--a`, тест на автоснятие двойного
минуса писать заново: `--a <=> a` на `x + (-(-2)) == 0` должно давать
`x + 2 == 0`.

### 8. `attr replace` — атрибут без потребителя

`RuleAttr::Replace` разбирается парсером и хранится в правиле, но нигде
в решателе не читается: вне `FromStr` (`rule_attribute.rs:34`) и ассерта
в тесте парсера (`parser/rule.rs:312`) упоминаний нет. Правила в
`symbols/*.sym`, помеченные `replace` (например `sqrt(a^2) => abs(a)` в
sqrt.sym), ведут себя как обычные.

Ретайр исходного терма (`mark_replaced`, `solver.rs:231`) выполняет
`try_simplify` по результату transform-упрощения — к атрибуту это
отношения не имеет.

Набросок: решить, что `replace` должен был значить, и либо реализовать,
либо убрать из языка вместе с пометками в `.sym`. Пока он вводит в
заблуждение при чтении правил.

Найдено при реализации `doc/ru/domain.md` фазы 1 (там же §4 — почему
гард «project несовместим с replace» не заводился).
