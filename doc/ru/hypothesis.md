# Гипотезы и конкретизация

При применении правила к терму система не сразу получает готовый
вывод — она проходит через промежуточный объект, **гипотезу**, в
котором уже выполнена подстановка параметров, но ещё не доказаны
ограничения и могут оставаться несвязанные параметры. Доводка гипотезы
до состояния, пригодного к проверке, называется **конкретизацией**
(grounding).

## Структура гипотезы

`Hypothesis` (`solver::rule::hypothesis::Hypothesis`):

| Поле | Назначение |
|------|------------|
| `rule: SharedRule` | Породившее правило. |
| `resolution: TermBuf` | Вывод правила после применения частичной подстановки параметров. |
| `params: ParamSubstitution` | Уже связанные параметры. |
| `requirements: Vec<TermBuf>` | Ограничения правила после применения частичной подстановки. |
| `free_params: HashSet<Param>` | Параметры, которые ещё не связаны. |
| `blocked_rules: Vec<RuleId>` | Правила из атрибута `block(...)` исходного правила (передаются результату). |

`GroundedHypothesis` — то же без `free_params`: гарантия, что все
параметры связаны.

В литературе соответствует:

| Понятие | Литературный термин |
|---------|---------------------|
| `Hypothesis` со свободными параметрами | non-ground clause |
| `GroundedHypothesis` | ground instance |
| `Hypothesis::ground()` | grounding / instantiation / означивание |
| `free_params` | free variables / свободные переменные |

## Откуда берутся свободные параметры

При применении правила параметры шаблона связываются с подтермами
обрабатываемого терма (унификация). Однако правило может вводить
**параметры, не входящие в шаблон**, — обычно через ограничения вида
`param == выражение` или `param in set(...)`. Эти параметры остаются
свободными после унификации; их значения должны быть найдены отдельно.

Типичные случаи:

- Локальные обозначения: `(b^2 - 4*a*c) as D` — параметр `D` появляется
  в выводе, но не в шаблоне.
- Перебор кандидатов: `u in divisors(d)` — параметр `u` принимает
  значения из множества.
- Промежуточные результаты: `poly_div(F, x - u) == Q` — параметр `Q`
  связывается значением калькулятора.

## Семантика операторов в требованиях

### `==` — двунаправленное связывание

Если одна из сторон `==` — параметр, а другая не содержит свободных
параметров, требование даёт **связывание**: параметр получает значение
противоположной стороны, а сам требование исчезает.

Сторона, на которой стоит параметр, не важна: `param == term` и
`term == param` обрабатываются одинаково. Если оба операнда — параметры
или ни один не свободен, требование считается обычным предикатом и
проверяется по обычной схеме.

Реализация: `Hypothesis::bind_equality_params`.

### `in` — предикат или генератор

Семантика зависит от того, связан ли левый аргумент:

| Левый аргумент | Роль | Что делает |
|----------------|------|------------|
| Связан | Предикат | Проверяет, принадлежит ли выражение множеству. |
| Свободный параметр | Генератор | Перебирает элементы множества, связывая параметр. |

Текущая реализация конкретизации **извлекает только генераторы вида
`param in set(...)`** — то есть множество должно быть синтаксически
задано как `set(e₁, e₂, …)`. Реализация: `Hypothesis::extract_generators`.

## Алгоритм конкретизации

`Hypothesis::ground()` принимает гипотезу и возвращает множество
конкретизированных гипотез (возможно пустое):

1. **Нормализация требований.** Каждое требование нормализуется
   (см. [normalization.md](normalization.md)); требования, ставшие
   тривиально истинными (`Truth::True`), отбрасываются.
2. **Итеративное связывание `==`.** Из требований извлекаются те,
   что имеют вид `param == term` или `term == param`. В цикле
   выбираются те, в которых противоположная сторона не содержит
   свободных параметров, — параметр связывается, его значение
   подставляется во всю гипотезу (включая остальные требования).
   Цикл повторяется, пока не останется ни одного связываемого.
   Оставшиеся возвращаются в `requirements` как обычные предикаты.
3. **Если все параметры связаны** — выдаётся
   `GroundedHypothesis` с очищенными требованиями.
4. **Иначе — генераторы.** Извлекаются требования вида
   `param in set(...)`. Если их нет — гипотеза отбраковывается
   (нет способа доназначить).
5. **Декартово произведение.** Для каждой комбинации значений
   генераторов:
   - подставляются значения,
   - повторно запускается шаг 2 (новые `==` могут стать связываемыми
     благодаря подстановке),
   - если в результате гипотеза стала grounded — она сохраняется.

```
function ground(h):
    bind_equality_params(h)
    if h is grounded: return [h]
    gens = extract `param in set(...)` from h.requirements
    if gens is empty: return []
    result = []
    for combo in cartesian_product(gens):
        h' = h with combo applied
        bind_equality_params(h')
        if h' is grounded: result.append(h')
    return result
```

## Пример

Правило поиска рациональных корней многочлена (см.
[rational_roots.md](rational_roots.md)):

```
F == 0 =>
    (x == u) || (Q == 0);

is_polynomial(F, x),
free_term(F, x) == d,
d != 0,
u in divisors(d),
substitute(x == u, F) == 0,
poly_div(F, x - u) == Q;
```

Шаблон содержит параметр `F`; параметры `d`, `u`, `Q` — свободные.
Применим правило к терму `x^3 - 6x^2 + 11x - 6 == 0`.

После унификации:

```
F = x^3 - 6x^2 + 11x - 6
free_params = {d, u, Q}
requirements = [
  is_polynomial(F, x)        → нормализуется до true → отбрасывается
  free_term(F, x) == d       → -6 == d
  d != 0
  u in divisors(d)
  substitute(x == u, F) == 0
  poly_div(F, x - u) == Q
]
```

Шаг 2 связывает `d ← -6`. После подстановки:

```
free_params = {u, Q}
requirements = [
  -6 != 0                    → true → отбрасывается
  u in divisors(-6)          → set(-6, -3, -2, -1, 1, 2, 3, 6) — генератор
  substitute(x == u, F) == 0
  poly_div(F, x - u) == Q
]
```

Параметры остались — переход к генераторам. Извлекаем `u in set(...)`,
для каждой комбинации (по 8 значений):

- При `u = 1`: `substitute(x == 1, F) == 0` нормализуется до `0 == 0` → отбрасывается.
  `poly_div(F, x - 1) == Q` → `Q ← x^2 - 5x + 6`. Все параметры связаны.
- При `u = -6`: `substitute(x == -6, F) == 0` нормализуется до `-504 == 0` → ложь, остаётся как непроверенное требование (будет отвергнуто на этапе обоснования).

Полученные конкретизированные гипотезы передаются дальше — на проверку
оставшихся ограничений через `Prove`-подзадачи (см.
[work_principle.md](work_principle.md#применение-правила-к-терму)).

## Альтернатива: грouninding через подзадачу `find`

Текущая реализация связывает параметры локально (итеративные `==` плюс
декартово произведение генераторов). Этот подход быстр, но ограничен в
ситуациях со связанными генераторами, например:

```
u in set(1, 2, 3),
v in set(4, 5, 6),
u + v == 7
```

Здесь полный перебор комбинаций — 9, и фильтр по `u + v == 7`
происходит после.

Альтернативный подход — формировать `find(free_params)`-подзадачу с
требованиями в качестве условий и делегировать решение солверу. Это
даёт распространение ограничений (constraint propagation), но требует
доработки механизма `is known`. Подход исследовался в ветке
`grounding-via-find-subtask`; в основной ветке не используется.
