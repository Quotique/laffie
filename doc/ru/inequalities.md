# Доказательство неравенств

Документ описывает, как решатель доказывает неравенства класса «знаки и
числовые оценки», и на какие слои разбита эта поддержка. Опирается на
[work_principle.md](work_principle.md) (bidirectional-поиск, Equivalence-
переписывание цели), [hypothesis.md](hypothesis.md) (grounding, requirements)
и [rule_syntax.md](rule_syntax.md).

## Текущее состояние

Символы сравнения `>`, `>=`, `<`, `<=` (`symbols/greater.sym`,
`greater_or_eq.sym`, `lesser.sym`, `lesser_or_equal.sym`) исходно содержали
только объявление `symbol ... { attr infix(400),display("..."); }` без правил.
Truth-checker'ы этих символов (`src/solver/term/symbol/base/{more,less,
more_or_equal,less_or_equal}.rs` → `compare_numbers` в `base/mod.rs`)
сравнивают только два числовых литерала; любое символическое сравнение даёт
`Truth::Unknown`.

Ответ prove-задачи фиксируется в `check_prove_answer`
(`src/solver/task/solver.rs`) при фокусе НЕ-goal-терма: ответ засчитывается,
если выведенный терм синтаксически совпал с одним из goal-термов, либо
какой-то goal-терм свёлся к `truth().is_true()`.

Отдельно `check_if_answer` при фокусе самого goal-терма prove-задачи сканирует
`goal_index` на тривиальную истину (`truth().is_true()`) и засчитывает ответ,
не требуя не-goal-терма. Поэтому чисто символическая цель, сводимая правилами
к `true` (например `x^2 >= 0`), решается без условий; фиктивные условия вроде
`t == 0` больше не нужны. Прежняя развязка «раздельного хранения целей и
условий» устранена.

## Канонические соглашения

- **Глобальной канонизации нет.** Мы не сводим `a > b` к `a - b > 0` и не
  приводим `<` к `>`. Такая канонизация сломала бы существующие prove-правила
  в `sqrt.sym`/`divide.sym` и ветвления по знаку в `abs.sym`/`logic_and.sym`,
  где обе ориентации неравенств используются как условия case-split.
- **Квадрат плюс константа — специфичным правилом, не общим переносом.**
  `x^2 + 1 > 0` доказывается правилом `a^2 + c > b <=> true; c is known,
  b - c < 0` (корень паттерна — `a^2 + c`). Общий перенос константы
  `a + c > b <=> a > b - c` пробовался, но он срабатывает на линейных
  ОДЗ-условиях find-задач (`x + 3 >= 0` после разбора sqrt-уравнения) и
  комбинаторно взрывал поиск (регресс `tasks/regress/irrational`) — поэтому
  отвергнут в пользу узкого правила про `a^2 + c` (см. «Отброшенные
  подходы»).
- **Ориентации не мостятся отражениями (`a > b <=> b < a`).** Отражения тоже
  пробовались и тоже отброшены: `a > b <=> b < a` (в `greater.sym`) и
  `a < b <=> b > a` (в `lesser.sym`) — взаимно-обратные правила, гоняющие цель
  между ориентациями по кругу (пинг-понг), что комбинаторно раздувало поиск на
  символических сравнениях в find-подзадачах. Пересечение ориентаций для
  числовых границ закрывает слой 2 (`bound_implies`), а целевой корпус этапа 1
  сам по себе однонаправлен (все цели уже в «естественной» ориентации своих
  правил).
- **Правило лежит в файле корня своего ПАТТЕРНА (левой части).** RulesEngine
  индексирует правила по корневому символу паттерна. Правило
  `a * c > 0 => ...` кладётся в `greater.sym`.

## Слой 1: правила (этот этап)

Набор правил в четырёх `symbols/*.sym`. Инварианты корректности:

- **`<=>` — только настоящая эквивалентность.** Правило с `<=>` несёт атрибут
  `Equivalence` и всегда применяется в одну сторону — паттерн→резолюция (реверс
  не генерируется). Отличие от `=>` в том, ГДЕ оно применяется: к goal-терму
  prove-задачи пропускаются только `<=>`-правила (фильтр в `suggest_rules`,
  solver.rs:243), `=>` там отсекаются. При этом одно и то же `<=>`-правило
  работает в двух ролях: (1) переписывание цели `G → R` на goal-терме —
  корректно лишь если `R ⟹ G`; (2) forward-вывод на не-goal терме (факте) —
  нужно `pattern ⟹ resolution`. Обе роли вместе требуют истинной
  эквивалентности. Пример допустимого: `a^2 + c > b <=> true` при `b - c < 0`
  (истинны обе импликации). Пример НЕдопустимого (unsound): `a + b > 0 <=> b > 0`
  при `a >= 0` — направление `true→(b>0)` вывело бы `y > 0` из `x + y > 0,
  x >= 0`.
- **`=>` — направленная импликация pattern ⟹ resolution.** Применяется forward
  к условиям/выведенным (не-goal) термам; к goal-терму prove-задачи НЕ
  применяется (его направление для переписывания цели было бы unsound). Так
  оформлены транзитивность, суммы оценок, знаки произведения.
- **Goal-унификация связывает свободные параметры.** `goal(prove(<pattern>))`
  унифицирует параметры правила с фактической целью задачи
  (`Rule::goal_mapping`), поэтому параметр резолюции/требований, отсутствующий
  в паттерне, легально связывается из цели. Именно так работает ослабление
  границы `a > b => a > c; b >= c;` с `goal(prove(a > c))`: `a, c` — из цели,
  `b` — из сматченного условия, `b >= c` доказывается Prove-подзадачей. Без
  goal-унификации свободный параметр в requirements отбросил бы гипотезу при
  grounding'е.

Все правила слоя стоят под `goal(prove(...))`-гейтом: в find/transform-задачах
`goal_mapping` не проходит и правила инертны.

## Слой 2: импликация числовых границ в Rust (этот этап)

`check_prove_answer` дополнен проверкой `bound_implies(derived, goal)`:
выведенный терм-неравенство с числовой границей принимается как доказательство
цели, если импликация границ выполнена для того же выражения. `E > c₁` доказывает
`E > c₂`/`E >= c₂` при `c₁ >= c₂` (со строгостью, ослабляемой в нужную сторону);
для верхних границ зеркально.

Зачем отдельный слой при живых правилах: он не зависит от уровней и циклов
поиска, срабатывает в том числе внутри Prove-подзадач требований (где условие
`x > 2` должно закрыть требование `x > 0`), и дёшев — простое числовое
сравнение без порождения новых термов. Он же закрывает пересечение ориентаций
для числовых границ (`0 < x` ⊢ `x > 0`: число слева переворачивает вид границы
в `as_bound`), заменяя отброшенные отражения.

Реализация: `as_bound` (парсит сравнение в выражение + вид границы + число),
`bound_implies` (импликация для одинаковых выражений и видов границ) в
`src/solver/task/solver.rs`.

## Слой 3 (отложен): знаковый truth-checker

Эскиз: рекурсивная `sign(TermRef) -> {Pos, NonNeg, Neg, NonPos, Zero,
Unknown}` в `base/mod.rs`, подключаемая в truth-checker'ы четырёх сравнений
(`a > b` истинно, если `sign(a - b) == Pos`, и т. п.).

Почему отложен: на целевом классе задач он дублирует правила слоя 1; при этом
`truth()` стоит в fast-path проверки ВСЕХ требований (`prove` в solver.rs), так
что ошибка в знаковой оценке молча «доказала» бы ложные требования по всему
корпусу — без шага в трейсе, который можно было бы заметить. Критерий
включения: задачи этапа 2 с n-арными суммами, где чисто-правиловый подход
взрывается комбинаторно.

## Слой 4 (будущее): интервальный движок

Оценка произвольного терма в интервал по границам переменных из контекста
задачи (`x > 2, y > 1 ⊢ x + y ∈ (3, +∞)`), с распространением интервалов через
арифметику. Обобщает слой 2 на нечисловые границы и n-арные выражения.

## Известные ограничения

а. **Переписанная цель + goal-унифицированное правило не компонуются.** При
   подборе правил для НЕ-goal-термов используется исходная цель задачи, а не
   её Equivalence-переписывания (solver.rs, `suggest_rules`). Поэтому цепочка
   «цель переписана правилом A → к результату применимо goal-унифицированное
   правило B» не строится. Пример: `prove(x / y > 0)` при `x > 0, y > 0` не
   решается — переписать цель к `x * y > 0` можно, но знаковое правило
   произведения к переписанной цели уже не подберётся.

б. **Полный квадрат не выделяется.** transform-подзадача, наоборот,
   разворачивает `(x - 1)^2` (binomial_unfold из `power.sym`), поэтому цели
   вида `prove((x - 1)^2 + 3 > 2)` этап 1 не берёт.

в. **Семантической импликации между произвольными термами нет** — только слой
   2 для числовых границ.

## Отброшенные подходы

Проверены на корпусе и отклонены — не возвращать без решения указанной причины:

- **Отражения `a > b <=> b < a` (и три аналога).** Пары взаимно-обратных правил
  (`a > b <=> b < a` в `greater.sym` и `a < b <=> b > a` в `lesser.sym`;
  аналогично `>=`/`<=`) гоняют цель между ориентациями по кругу — пинг-понг,
  который на символических сравнениях в Prove-подзадачах find-задач раздувал
  поиск на порядки. Итог: `find(sqrt(x)==2)` переставал решаться, а
  `tasks/regress/irrational` упирался в дедлайн. Соундность отражений при этом
  не нарушалась — проблема чисто в разрастании поиска. Числовые мосты закрыл
  `bound_implies`; символических мостов этап 1 не требует.

- **Общий перенос константы `a + c > b <=> a > b - c` (`c is known`).**
  Срабатывает не только на цели `x^2 + 1 > 0`, но и на линейных ОДЗ-условиях
  find-задач (`x + 3 >= 0` после разбора sqrt-уравнения); в связке с
  sqrt-разбиением взрывал `tasks/regress/irrational` (4 задачи упирались в
  дедлайн циклов). Заменён узким `a^2 + c > b <=> true; c is known, b - c < 0`
  (и `>=`-аналогом), который матчит только `a^2 + c` и линейные условия не
  трогает.

## Дорожная карта

- **Этап 2:** n-арный знаковый анализ сумм; монотонное масштабирование
  `a > b, c > 0 ⊢ a*c > b*c`; произведение оценок; знаковый truth-checker
  (слой 3) как замена комбинаторно-взрывающимся правилам.
- **Этап 3:** интервальный движок (слой 4); выделение полного квадрата;
  классические неравенства (AM-GM и т. п.).

Кандидаты этих этапов лежат в `tasks/unsolved/inequalities.pbl`.
