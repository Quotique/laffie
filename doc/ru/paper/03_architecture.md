## 3. Архитектура и механизм делегирования

### 3.1. Концептуальная схема

Гибридная схема состоит из трёх этапов, циклически применяемых до
получения ответа:

1. **Логический шаг** (логический слой системы). Задача
   преобразуется по правилам термового переписывания, пока не
   возникает шаг, требующий тяжёлой алгебраической арифметики или
   перебора по конечному множеству значений.
2. **Делегирование** (детерминированный калькулятор). Подзадача с
   однозначно определённым ответом передаётся процедурному символу
   — реализации детерминированного контракта (см. §3.2). Реализация
   может быть встроенной в саму систему либо обёрткой над внешней
   системой компьютерной алгебры.
3. **Сборка** (логический слой системы). Полученные результаты
   возвращаются в задачу как новые термы или фиксируются как ветви
   дизъюнктивного ответа; цикл повторяется.

Калькулятор в этой схеме — не конкретная система, а контракт:
функция от запроса, представленного термом, к детерминированному
ответу — значению, конечному множеству или булевой проверке. Любой
алгоритм, реализующий такой контракт, может быть подключён через
единообразный архитектурный механизм, описанный в §3.2.

В настоящей работе рассмотрены две формы делегации, различающиеся
гранулярностью — объёмом подзадачи, передаваемой одному вызову
калькулятора.

- **Мелкозернистая делегация** — несколько узких процедурных символов
  в одном правиле, каждый отвечает за одну детерминированную операцию.
  Пример: правило поиска рациональных корней многочлена с пятью
  символами `divisors`, `is_polynomial`, `free_term`, `substitute`,
  `poly_div`. Реализация процедурных символов в этом примере
  смешанная: часть встроена в саму систему, часть — обёртки над
  SymPy, использующие CAS как вспомогательный движок для отдельных
  полиномиальных операций. Логика теоремы (разбор случаев по
  делителям, отсев по корню, редукция степени) реализована
  декларативным правилом и полностью лежит на стороне логического слоя.
- **Крупнозернистая делегация** — один процедурный символ обрабатывает
  целую подзадачу. Пример: `sympy_solve(eq, x)` — обёртка над SymPy.
  Правило в этом случае сводится к параметрической обвязке вокруг
  вызова калькулятора (например, разбор случаев по обнулению
  коэффициентов).

Архитектурный смысл такого разделения — в инвариантности механизма
делегирования относительно гранулярности и относительно реализации
конкретного процедурного символа. Правило, использующее много мелких
калькуляторов смешанного происхождения, и правило, использующее один
крупный CAS-вызов, опираются на одну и ту же четырёхблочную палитру
из §3.2; конкретное правило выбирает подмножество блоков, согласное
со структурой задачи (см. контраст rational_roots и C1 в §3.2 и §7).
Различие — в распределении работы между логическим слоем и
калькуляторами.

### 3.2. Механизм делегирования

Процедурный символ — архитектурный элемент, добавляемый к логическому
ядру системы настоящей работой. Тело символа — функция, реализующая
детерминированный алгоритм; внешний интерфейс — терм-выражение.
Правило взаимодействует с процедурным символом тем же синтаксисом,
которым оно взаимодействует с любым другим термом в шаблоне или
требованиях; никаких особых конструкций для вызова делегата в языке
правил не предусмотрено. Это и обеспечивает встраивание процедурных
символов в декларативные правила без процедурного контроля потока.

В качестве сквозного примера используется правило поиска
рациональных корней многочлена. Теоретическое основание — классическая
теорема: монический многочлен с целыми коэффициентами имеет
рациональным корнем только целочисленный делитель свободного члена.
Правило формализует следствие теоремы как редукционный шаг:

```
rule {
    attr level(5), goal(find(x, ..));

    F == 0 =>
        (x == u) || (Q == 0);

    is_polynomial(F, x),
    free_term(F, x) == d,
    d != 0,
    u in divisors(d),
    substitute(x == u, F) == 0,
    poly_div(F, x - u) == Q;
}
```

Шаблон правила `F == 0` связывает параметр `F` с многочленом из
условий задачи. Резолюция `(x == u) || (Q == 0)` фиксирует найденный
корень в левой ветви и редуцирует задачу к многочлену меньшей степени
в правой. В требованиях задействованы пять процедурных символов:
`is_polynomial`, `free_term`, `divisors`, `substitute`, `poly_div`.
Реализация символов разнородна: часть встроена в ядро системы, часть
— обёртки над SymPy. С точки зрения правила это различие не
существенно: все пять предъявляют единый интерфейс — терм-выражение,
возвращающее терм или конечное множество.

Структура взаимодействия правила с процедурными символами
раскладывается на четыре строительных блока.

**Связывание по генератору.** Процедурный символ возвращает конечное
перечислимое множество; в требовании правила параметр связывается с
элементом этого множества через ключевое слово `in`. В примере:
`u in divisors(d)` — параметр `u` пробегает делители числа `d`,
выданные калькулятором `divisors`. Связывание по генератору
реализует разбор случаев по конечному множеству без явной директивы
ветвления; ветви раскрываются декартовым произведением механизмом
конкретизации.

**Пост-фильтр калькулятора.** Процедурный символ возвращает значение,
сравниваемое с константой или другим связанным термом в требованиях;
ветви, не прошедшие проверку, отбрасываются до резолюции. В примере
пост-фильтр появляется в трёх формах: `is_polynomial(F, x)` — булева
предикатная проверка применимости правила; `d != 0` — сравнение
связанного значения с константой; `substitute(x == u, F) == 0` —
наиболее интересный случай: пост-фильтр после связывания по
генератору, отсеивающий перебранные кандидаты `u`, не являющиеся
корнями. Все три формы — частные случаи общего механизма «процедурный
символ → условие в требованиях».

**Конкретизация параметров правила.** Параметры правила связываются
стандартным итеративным механизмом системы. На каждой итерации
просматриваются требования вида `t == p`, где `p` — свободный
параметр, и выполняется связывание; новые связанные параметры
раскрывают дополнительные требования на следующей итерации.
Декартово произведение раскрывается над параметрами, связанными
через связывание по генератору. В примере порядок связывания: `F`
(из шаблона) → `d` (из `free_term(F, x) == d`) → `u` (из генератора
`u in divisors(d)`) → `Q` (из `poly_div(F, x - u) == Q`).
Последовательность восстанавливается автоматически из структуры
требований; в самом правиле никакого процедурного контроля потока
нет.

**Дизъюнктивная резолюция.** Правая часть правила —
`(x == u) || (Q == 0)` — формирует дизъюнктивный ответ из ветвей,
найденных правилом. Левая часть фиксирует один корень, правая
сводит задачу к многочлену меньшей степени, который обрабатывается
рекурсивным применением правил. Дизъюнктивная резолюция —
единственный способ, которым разбор случаев проявляется
синтаксически в тексте правила; в остальном правило остаётся
синтаксически конъюнктивным.

Все четыре блока проявлены в одном правиле: rational_roots
демонстрирует мелкозернистую делегацию, использующую полную палитру.
В §7 разбирается крупнозернистый случай (`sympy_solve` как
единственный калькулятор на всю подзадачу) — там в правиле
проявляются только два блока из четырёх (конкретизация параметров
+ дизъюнктивная резолюция), что и иллюстрирует «выбор подмножества»
из заявленной выше инвариантности.

### 3.3. Вызов подзадачи из правила

Параллельно описанному выше механизму процедурных символов система
поддерживает явный вызов подзадачи из правила. Базовый механизм
подзадач описан в [TODO: cite Solver-paper]: подзадача —
вспомогательная задача, решаемая независимо в рамках текущей сессии
с теми же типами целевых установок (`find`, `prove`, `transform`),
результат которой возвращается в основную задачу. Подзадачи
кэшируются по контентному ключу и могут рекурсивно создавать
собственные подзадачи с ограничением глубины вложенности.

Настоящая работа дополняет этот механизм **явным синтаксисом вызова
подзадачи из требования правила**. В требованиях правила может
стоять блок вида `find(vars) { eqs; ... }`, обозначающий запуск
нового сеанса решения на сформированной подзадаче поиска значений
переменных `vars` при заданных условиях `eqs`. Ответ подзадачи
связывается с параметром правила, который далее участвует в его
выводе.

Внутреннее представление блока — терм-выражение `solve(find(vars),
eqs...)` с отдельным головным символом `solve`, отделяющим
суб-вычисление от обычной целевой установки `find` основной задачи.
При наличии требования `solve(find(vars), eqs...) == p` решатель
запускает новый сеанс работы на сформированной подзадаче, наследуя
известные параметры родительской задачи с фильтром по неизвестным
термам подзадачи. Полученный ответ — со снятой оболочкой
`answer(...)` — связывается с параметром правила `p` и используется
в выводе.

Защита от бесконечной рекурсии — кэш сеансов суб-решения,
индексированный полным выражением `solve(find(vars), eqs...)` как
контентным ключом. При повторном вхождении той же формы (например,
правило, делегирующее свою же сигнатуру в одной из ветвей разбора)
вместо нового сеанса возвращается маркер «решение не найдено», что
обрывает рекурсивную ветвь. Подзадачи с другой структурой — меньшая
степень многочлена, иная конфигурация параметров — получают свежие
ключи и решаются нормально.

Пример сочетания этого механизма с обращением к процедурному символу
приведён в §5.1 на карточке C2.
