## План реализации параметрического каталога (Phase 1)

Артефакт Phase 0 — каталог из 12 параметрических карточек, типология
приёмов, сетка покрытия и outline статьи в
[`parametric_catalog.md`](parametric_catalog.md).

Цель Phase 1 — рабочая система в laffie + черновик статьи с разбором 1–2
эталонных кейсов.

Базовый паттерн реализации: rule-based laffie + PyO3-bridge к SymPy через
procedural symbol с `py "..."` блоком и declarative rule с `||` в
резолюции. Точное состояние bridge-инфраструктуры устанавливается на
шаге 1.

Список задач в порядке очерёдности; распределение по времени не
фиксируется.

### Подготовка инфраструктуры

1. **Архитектурное расследование текущего laffie.**
   - PyO3-bridge: `src/parser/symbol.rs`, файлы `symbols/py/*.py`.
     Запускается ли SymPy embed-режимом, какие term ↔ SymPy конверсии
     уже работают.
   - Эталонные procedural-symbol файлы: `symbols/poly_div.sym`,
     `doc/ru/rational_roots.md` (если упомянутый паттерн актуален).
   - Текущее представление ответа в solver (одиночный термин / set /
     дизъюнкция через `||`).
   - Синтаксис `find(x)` для задач со свободным параметром — как
     параметр объявляется в дано / условиях.
   - Находки зафиксировать в новом разделе `## Архитектурный обзор`
     этого файла либо в отдельном `doc/ru/architecture_state.md`.
   - **Возможный re-plan.** Если архитектура существенно отличается от
     ожидаемого паттерна (procedural symbol + decl rule с `||`), задачи
     2–12 требуют ревизии до начала реализации.

2. **Представление `x ∈ ℝ` в ответе.**
   Сейчас не выражается. Ввести минимальный механизм: ответ задачи может
   принимать форму «любое вещественное» и solver принимает это как
   валидное завершение ветви. Контрольная задача — тождество `0·x = 0`
   с ответом `x ∈ ℝ`. Тест в `cargo test --workspace` (unit) и/или
   `.pbl` интеграционно.

3. **Обработка пустой ветви в дизъюнкции.**
   Вероятно не реализовано. Семантика: пустая ветвь даёт «нет решений в
   этой ветви» в кусочном ответе (требуется для C24, C28). Контрольная
   задача — конкретный случай, в котором одна из ветвей заведомо пуста.
   Тест на интеграционном уровне (`.pbl`).

### Реализация эталонной карточки

4. **Procedural symbol `sympy_solve(eq, x)`.**
   Минимальный wrapper над `sympy.solve` для конкретного уравнения и
   неизвестной. Расширение `symbols/py/sympy_convert.py` для нужных
   операторов (минимум `==`). Тест unit-уровня: на конкретных уравнениях
   (`x² − 4 = 0` → `±2`) через bridge возвращаются ожидаемые term-ы.

5. **C1 end-to-end.**
   - Задача в `tasks/sympy_comparison/parametric/c1.pbl`: «решить
     `a·x = a` относительно `x`».
   - Правило в новом `.sym` файле: шаблон `p·x == q` с requirement-ами и
     резолюцией через `||` (ветви `p = 0` и `p ≠ 0`).
   - Делегирование SymPy в ветви `p ≠ 0`; ветвь `p = 0` через `q = 0` /
     `q ≠ 0` без CAS.
   - Интеграционный тест на `.pbl`: laffie возвращает кусочный ответ
     `(a = 0 ∧ x ∈ ℝ) ∨ (a ≠ 0 ∧ x = 1)`. Контрольное сравнение: чистый
     SymPy на той же задаче даёт только `[1]`.

### Реализация case-split-семейства

6. **Следующие case-split карточки (минимум две).**
   Тезис «семейство приёмов» подкрепляется не одной, а несколькими
   карточками с разными механизмами ветвления. Минимум:
   - **C24** — два независимых вырождения параметра, минимальное
     расширение C1.
   - Одна из {**C2** (двухуровневый разбор), **C26** (факторизация +
     знак)} — выводит за рамки одного приёма.
   
   Под каждую карточку — `.pbl`-задача и интеграционный тест аналогично
   шагу 5.

### Реализация постпроцессинга

7. **Постпроцессинговый примитив.**
   Перед карточкой нужен общий механизм; выбор зависит от того, какая
   карточка выбрана в шаге 8:
   - Для **C29** — механизм «формальное решение SymPy → постфильтр
     предикатом» (приём ОДЗ-фильтра).
   - Для **C28** — CAS-минимум на piecewise-функции (через
     `sympy.minimum` или эквивалент). Дополнительно — механизм
     знак-разбора модулей в кусочно-линейную форму.
   
   Это самостоятельная инфраструктурная задача, отдельная от карточки.
   Тест unit-уровня на корректность примитива.

8. **Постпроцессинговая карточка.**

## Архитектурный обзор (после task 1)

Расследование завершено. Базовый паттерн памяти подтверждён, re-plan
задач 2–12 не требуется. Ниже — что подтверждено и какие точки остались
открытыми.

### Подтверждено

1. **PyO3-bridge активен** — `src/parser/symbol.rs:42–93` использует
   `Python::initialize()` + `Python::attach()` (embed, не subprocess).
   Term ↔ Python через JSON-сериализацию `TermBuf`. Калькулятор в Python
   получает обёрнутый `Term` и `level`-строку, возвращает `None`
   (без изменений) или новый `Term`.

2. **Procedural symbol pattern работает.** Эталон —
   `symbols/poly_div.sym`. Структура:
   ```
   symbol N {
       py "
   exec(open('symbols/py/sympy_convert.py').read())
   def calculator(root, level):
       ...
   ";
   }
   ```

3. **Конвертер `symbols/py/sympy_convert.py` существует** с функциями
   `to_sympy(node, var_map)` и `from_sympy(expr, var_name, Term)`.
   Поддерживаются операторы: `+`, `*`, `^`, `/`, `neg`. **Не
   поддерживаются:** `==`, `!=`, `<`, `>`, `<=`, `>=`, `Abs`, sqrt
   (отдельный символ), тригонометрия, логарифмы.

4. **Дизъюнкция `||` в резолюции правила работает.** Эталон —
   `symbols/power.sym` (теорема о рациональных корнях):
   `F == 0 => (x == u) || (Q == 0)`. Документировано в
   `doc/ru/rational_roots.md`.

5. **Grounding** через `Hypothesis::ground()`
   (`solver/rule/hypothesis.rs:48`) — equality binding + cartesian
   product по generator-ам `param in set(...)`.

6. **Goal types:** `find(x)`, `find(x, y, ...)`, `prove(p)`,
   `transform(t)`. Multi-var find собирает конъюнкцию ответа
   (`x == 3 && y == -2`).

7. **Формат ответа в `.pbl`:** `answer X, Y;` — список альтернативных
   форм. Решатель принимает любую совпавшую.

8. **Параметр в задаче — свободная переменная.** Подтверждено
   пользователем; в коде это `Param` (отличный от `Variable`,
   которая — то, что ищем). Param появляется через unification правил.

### Неподтверждено / открытые точки

A. **Отсутствует представление `x ∈ ℝ`.** Существующий `set` (в
   `symbols/set.sym`) поддерживает только конечные множества (`set(a)`,
   `set(a, b)`, `set(a, b, ..)`). Нет символа `Reals` или эквивалента.
   Минимум — ввести нульарный символ (например, `R` или `Reals`) и
   правило-нормализацию «`x in R` — валидный ответ для `find(x)`».

B. **Условный ответ от параметра** — самый существенный риск.
   Текущие тесты имеют безусловный ответ (`x == 3`) или набор альтернатив
   (`x == -1 || x == 1`). Семантика «ответ зависит от значения
   параметра», вида `(a == 0 && x in R) || (a != 0 && x == 1)`,
   не зафиксирована в существующих задачах; принимает ли её
   `check_find_answer` (`solver/task/solver.rs:588`) — нужно проверить
   эмпирически на task 5. Если нет — потребуется доработка либо
   альтернативный формат (отдельный piecewise-символ).

C. **Поведение `||` с false-ветвью.** Резолюция вида
   `(0 == 4) || (x == 1)` должна сворачиваться к `x == 1`. Базовый
   `false` явно не определён (`logic_true.sym` есть, `false`
   реализуется через `!true`). Автоматический отсев противоречивой
   ветви не проверен — задача 3.

D. **Дизъюнкция в multi-var find** — известный TODO в
   `tasks/test/equation.pbl`: «дизъюнктивный ответ в multi-var find».
   Не критично для одиночных уравнений (наш основной фокус), но
   блокер для систем (C11, C21, C27) — поэтому они в task 10
   откладываются.

E. **Параметрический case-split в существующих правилах не реализован.**
   В `symbols/equal.sym` есть базовое правило
   `x*a + b == 0 => x == -b/a` с requirement `a != 0`. Этот
   requirement блокирует применение правила для параметрического `a` с
   неизвестным знаком. Нужно ввести альтернативное правило с
   дизъюнктивной резолюцией, явно вводящее ветви по обнулению `a`.

### Влияние на дальнейшие задачи

- **Task 2 (`x ∈ ℝ`)** — нужен новый zero-arity символ + рулевая
  поддержка для answer-checking. Не блокирует, но требует
  проектирования.
- **Task 3 (пустая ветвь)** — расширяется до проверки автоматического
  отсева false-веток в `||`. Возможно, потребуется правило-нормализация
  или модификация в `check_find_answer`.
- **Task 5 (C1)** — план остаётся, но на этом шаге проверяется открытый
  пункт B. Если решатель не принимает кусочный ответ как валидный,
  task 5 расширяется до доработки answer-checker.
- **Task 6, 7, 8** — не блокируются текущим состоянием, но реалистичны
  после закрытия 2 и 3.

Re-plan не запускается: существенных архитектурных сюрпризов нет.
