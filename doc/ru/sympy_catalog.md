## Каталог задач: провалы SymPy, поддающиеся rule-based координации

### Назначение

Документ — основной research-артефакт направления «гибридное решение через
делегирование SymPy» (план верхнего уровня — [sympy_delegation_plan.md](sympy_delegation_plan.md)).
Назначение каталога — собрать выборку задач, на которых SymPy объективно
проигрывает, классифицировать их по характеру провала и подходящему методу
rule-based рассуждения, и очертить scope потенциальной публикации.

Каталог должен давать конкретный объект для обсуждения и сужения scope.

### Таксономия

Двумерная сетка: **режим провала SymPy × тип rule-based рассуждения**.
Заполненные клетки определяют scope первой итерации.

#### Режимы провала SymPy

- **R1 — потеря случая**: SymPy делит на параметрический множитель и теряет
  решения при его обнулении.
- **R2 — лишние корни (нет ОДЗ)**: SymPy формально решает, не проверяя
  область определения; возвращает корни, не удовлетворяющие исходному.
- **R3 — неполное множество**: возвращает только конечное подмножество
  бесконечной серии решений (типично для тригонометрии под `solve`).
- **R4 — `NotImplementedError` / пустой ответ**: явный отказ или возврат
  пустого списка при наличии решения.
- **R5 — неверный ответ**: возвращает неверное значение (типично из-за
  сдвига ветви корня, неправильной классификации, упрощения с потерей).
- **R6 — отсутствие режима**: задача требует prove или анализа существования,
  для которых у SymPy нет публичного API.

#### Типы rule-based рассуждения

- **M1 — case-split по параметру**: явное ветвление по значению параметра.
- **M2 — case-split по знаку**: разбор по знаку выражения (модуль, sign,
  параметрические неравенства).
- **M3 — ОДЗ-tracking**: явное ведение области определения; отсев решений,
  не удовлетворяющих ОДЗ.
- **M4 — введение дискретного параметра**: расширение конечного набора
  решений за счёт явного введения дискретного параметра — целочисленного
  индекса серии (`x = a + bk, k ∈ ℤ` для тригонометрии) или индекса ветви
  многозначной функции (например, `n ∈ {0, −1}` для вещественных ветвей
  LambertW).
- **M5 — факторизация до тяжёлой машинерии**: явное разложение системы на
  ветви по факторизации до запуска Гребнера.
- **M6 — prove через тождества**: преобразование к заведомо положительному
  выражению (например, через `(a-b)² ≥ 0`).

## Verified карточки (SymPy 1.14.0)

Карточки сгруппированы по тиру — приоритету для аргумента публикации:

- **Тир 1** — гибрид (laffie + sympy) выигрывает там, где ни одна
  сторона в чистом виде не справляется. Основная масса аргумента.
- **Тир 2** — архитектурные пределы CAS, которые вряд ли исчезнут без
  рефакторинга sympy. Усиление тезиса о долгой ценности laffie.
- **Тир 3** — implementation gap, вероятно закроется в следующих
  версиях sympy; включены как baseline для версии 1.14.0.

Внутри тира карточки идут от наиболее интересных (cross-API,
реальные issue-failures) к более локальным.

Сетка покрытия R×M (выше) даёт ортогональный взгляд: одна и та же
ячейка может содержать карточки из разных тиров.

### Тир 1 — гибридная победа

Failure — координация (case-split, post-filter, факторизация, meta-extraction). Pure CAS не делает координацию; pure rule-based вынужден переписывать CAS-арифметику. Гибрид — точное попадание.

Внутри тира: открываем сильнейшими кросс-API кейсами и реальными issue-failures, переходим к стандартному параметрическому каноническому материалу, заканчиваем узкими специальными случаями.

#### C2 — параметрическое квадратное с двумя вырождениями

- **Постановка**: решить относительно `x` уравнение
  `(a² − 1)·x² + 2·(a − 1)·x + 1 = 0`.
- **SymPy**: возвращает формулы корней, в знаменателе — `(a² − 1)`,
  под корнем — `(2 − 2·a)`. При `a = 1` обе формулы вырождаются (знаменатель
  и подкоренное равны 0); при `a = −1` знаменатель = 0.
- **Ожидаемый ответ**:
  - `a = 1`: уравнение принимает вид `1 = 0` — решений нет.
  - `a = −1`: линейное `−4·x + 1 = 0` — `x = 1/4`.
  - иначе: квадратное общего вида.
- **Режим провала**: R1.
- **Метод laffie**: M1 — case-split на старший коэффициент `a² − 1` и на
  следующий по старшинству `2(a − 1)`. В каждой ветви задача редуцируется
  к виду, который sympy решает корректно (можно делегировать).
- **Источник**: локальная верификация (классическое параметрическое
  квадратное с двумя вырождениями старшего коэффициента).

#### C3 — система с факторизуемыми множителями (Issue #23637)

- **Постановка**: система двух полиномиальных уравнений из реального issue
  SymPy #23637 (упрощённая):
  ```
  1e-4·(x+2)·(4y+3x+1)³  =  1.3·(−2y−x+1)·(−y−x+1)·(2y+2x+6)²
  1e-4·(y+1)·(4y+3x+1)⁴  =  2.99·(−2y−x+1)²·(−y−x+1)·(2y+2x+6)²
  ```
- **SymPy**: возвращает только целочисленные решения
  `{(−11, 8), (−3, 2), (−2, −1), (5, −4)}`.
- **Ожидаемый ответ**: помимо целочисленных существуют нецелочисленные
  вещественные решения, например в окрестности `(1.32, −0.32)`.
- **Режим провала**: R4 — Гребнер обрывается на простых случаях.
- **Метод laffie**: M5 — предварительная факторизация общих множителей
  обеих частей, разложение в дизъюнкцию ветвей `(множитель = 0) ∨ ...`,
  делегирование каждой ветви sympy.
- **Источник**: SymPy issue [#23637](https://github.com/sympy/sympy/issues/23637).

#### C21 — `rref` сингулярной символьной матрицы делит на параметрический пивот

- **Постановка**: привести к ступенчатому виду матрицу
  ```
  ⎡−3ν     1          0          0⎤
  ⎢ 3ν   −2ν−1        2          0⎥
  ⎢ 0     2ν       −ν−λ−2        3⎥
  ⎣ 0     0         ν+λ         −3⎦
  ```
- **SymPy**: `A.rref()` возвращает первые три строки единичной формы с
  правым столбцом `[−1/(λν²+ν³), −3/(λν+ν²), −3/(λ+ν), 0]ᵀ`. То есть
  делит на множители `ν`, `ν²`, `(λ+ν)`, не сообщая об этом.
- **Ожидаемый ответ**: piecewise-результат:
  - в общем случае (`ν ≠ 0 ∧ λ + ν ≠ 0`) — указанная форма;
  - при `ν = 0` — ступенчатая форма с pivot-столбцами `(1, 2, 3)` (а не `(0, 1, 2)`);
  - при `λ + ν = 0` — ступенчатая форма с pivot-столбцами `(0, 1, 3)`.
- **Режим провала**: R1 — `rref` молча делит на параметрические выражения,
  теряя ветви, в которых эти выражения обнуляются. Нет общедоступного API,
  чтобы получить case-split-ответ.
- **Метод laffie**: M1 — case-split на старший pivot `ν`, далее на
  следующий `(λ + ν)`. Каждая ветвь сводится к `rref` без параметра в
  знаменателе и делегируется sympy.
- **Источник**: StackOverflow [#19072700](https://stackoverflow.com/questions/19072700).
- **Заметка**: расширяет R1×M1 за рамки `solve` — те же координационные
  провалы воспроизводятся в линейноалгебраических примитивах.

#### C23 — параметрический предел отказывается без значения параметра

- **Постановка**: `lim_{x → +∞} (x·e^x − e^{2√(1+x²)}) / (e^{α·x} + x^α)`
  при `α > 0`.
- **SymPy**: `limit(...)` возвращает невычисленный объект `Limit(...)`.
  При подстановке конкретных значений: `α = 2 → −1`, `α = 1/2 → −∞`,
  `α = 3 → 0`.
- **Ожидаемый ответ**: case-split по `α`:
  - `α < 2`: `−∞`;
  - `α = 2`: `−1`;
  - `α > 2`: `0`.
  Анализ: числитель ~ `−e^{2x}` (доминирует `e^{2√(1+x²)} ≈ e^{2x}`),
  знаменатель ~ `e^{α·x}`, отношение ~ `−e^{(2−α)x}`.
- **Режим провала**: R4 — `limit` не делает case-split по параметру и
  поэтому возвращает «no progress» (на конкретных значениях работает).
- **Метод laffie**: M1 — сравнение порядков роста как параметрический
  case-split: правило «`e^{kx}` с большим `k > 0` доминирует над
  `e^{mx}` при `k > m`», далее ветвление `α < 2 / α = 2 / α > 2` и
  делегирование вычисления sympy в каждой ветви.
- **Источник**: StackOverflow [#59995637](https://stackoverflow.com/questions/59995637).
- **Заметка**: пример того, что параметрический case-split нужен не
  только в `solve`, но и в `limit`. Аналог C10 (параметрическое
  неравенство) в анализе.

#### C14 — целочисленная диофантова система

- **Постановка**: найти целочисленные решения системы
  `{ a·b + c = 2020, a + b·c = 2021 }`.
- **SymPy**: `solve` возвращает континуум через корень
  `sqrt(4c² − 8080c + 4084441)` с `c` параметром.
- **Ожидаемый ответ**: дискретный набор целых решений, в частности
  `(a, b, c) = (673, 2, 674)` и `(2021, 0, 2020)` (Mathematica их
  находит).
- **Режим провала**: R3 — неполное множество (континуум вместо
  дискретного решения).
- **Метод laffie**: M5 + целочисленный поиск — факторизация
  `(a − c)·(b − 1) = 1`, разбор знаков, перебор делителей; SymPy
  работает на каждой ветви.
- **Источник**: SymPy issue [#24791](https://github.com/sympy/sympy/issues/24791).
- **Заметка**: в SymPy есть `diophantine`, но он не справляется с
  нелинейными системами такого вида.

#### C28 — нет API для «при каких `a` неравенство `f(x) < a` разрешимо»

- **Постановка**: при каких значениях `a` неравенство
  `|x − 1| + |x + 1| < a` имеет хоть одно решение?
- **SymPy**: `reduce_inequalities([|x−1| + |x+1| < a], [x])` →
  `NotImplementedError`. `solveset(..., S.Reals)` → `ConditionSet`.
  Дополнительно: `minimum(|x−1| + |x+1|, x)` тоже бросает
  `NotImplementedError: Unable to find critical points for Abs(x − 1) + Abs(x + 1)`,
  так что нельзя извлечь нижнюю границу даже через критические точки.
- **Ожидаемый ответ**: `a > 2` — поскольку `f(x) = |x−1|+|x+1| ≥ 2` везде
  (минимум достигается на `[−1, 1]`).
- **Режим провала**: R6 — нет режима «множество значений параметра, при
  которых неравенство разрешимо», и сопутствующая R4: `minimum` сам не
  справляется с суммой модулей.
- **Метод laffie**: M2 — разбор по знаку каждого выражения под модулем,
  получение явной кусочно-линейной формы `f(x)`, нахождение минимума
  через сравнение значений на участках; затем условие на `a`.
- **Источник**: Сканави.
- **Заметка**: продолжение C27 в M2-направлении. Заполняет ранее пустую
  клетку R6×M2. Бонусом — пример провала `minimum(...)` на простом
  выражении с суммой модулей; типично для семейства задач, где laffie
  должен взять знак-разбор на себя.

#### C1 — параметрическое линейное

- **Постановка**: решить относительно `x` уравнение `a·x = a`.
- **SymPy**: `solve(Eq(a*x, a), x)` → `[1]`.
- **Ожидаемый ответ**: при `a ≠ 0` единственное решение `x = 1`; при `a = 0`
  решение — любое вещественное `x`.
- **Режим провала**: R1 — `solve` молча делит на `a`, теряя случай `a = 0`.
- **Метод laffie**: M1 — правило для шаблона `p·x == q` с requirement-ами,
  явно разбивающими случаи `p=0 ∧ q=0`, `p=0 ∧ q≠0`, `p≠0`, и резолюцией
  через дизъюнкцию `||`.
- **Источник**: локальная верификация (классическое упражнение по разбору
  параметрического линейного уравнения).

#### C24 — `solve` теряет вырожденные случаи параметрического линейного

- **Постановка**: решить относительно `x` уравнение `(a² − 4)·x = a − 2`.
- **SymPy**: `solve(...)` → `[1/(a + 2)]`. `solveset` → `{(a − 2)/(a² − 4)}`
  (та же единственная ветвь без сокращения).
- **Ожидаемый ответ**: после факторизации `(a − 2)(a + 2)·x = (a − 2)`:
  - `a = 2`: `0 = 0`, `x ∈ ℝ`;
  - `a = −2`: `0 = −4`, решений нет;
  - иначе: `x = 1/(a + 2)`.
- **Режим провала**: R1 — `solve` молча сокращает `(a − 2)` и делит на
  `(a + 2)`, теряя обе вырожденные ветви.
- **Метод laffie**: M1 — case-split по `(a − 2)` и `(a + 2)`, в каждой
  ветви равенство сводится к виду без параметра в знаменателе.
- **Источник**: Сканави (параметрические уравнения).
- **Заметка**: расширение C1 — два независимых вырождения параметра
  вместо одного. Хороший минимальный пример «потеря двух случаев одним
  вызовом».

#### C10 — параметрическое неравенство

- **Постановка**: `a·x > b` относительно `x`, при произвольных вещественных
  `a, b`.
- **SymPy**: `reduce_inequalities([a*x > b], [x])` → `a·x > b` (без разбора).
- **Ожидаемый ответ**:
  - `a > 0`: `x > b/a`.
  - `a < 0`: `x < b/a`.
  - `a = 0, b < 0`: `x ∈ ℝ`.
  - `a = 0, b ≥ 0`: `x ∈ ∅`.
- **Режим провала**: R4 — отказ от разбора (возврат входа без обработки).
- **Метод laffie**: M1 + M2 — case-split по знаку `a` (с разворотом
  неравенства при отрицательном) и обработка вырожденного `a = 0`.
- **Источник**: собственная верификация.

#### C25 — параметрическое квадратичное неравенство — нет разбора

- **Постановка**: решить относительно `x` неравенство
  `a·x² + (a − 1)·x − 1 > 0`.
- **SymPy**: `reduce_inequalities([expr > 0], [x])` → `NotImplementedError:
  ... cannot be solved using solve_univariate_inequality`. `solveset(expr > 0,
  ..., S.Reals)` → `ConditionSet`.
- **Ожидаемый ответ**: после факторизации `(a·x − 1)(x + 1) > 0`,
  корни `x = 1/a` и `x = −1` (при `a ≠ 0`):
  - `a > 0`: `x < −1` или `x > 1/a`;
  - `a = 0`: `x < −1`;
  - `−1 < a < 0`: `1/a < x < −1`;
  - `a = −1`: `∅` (парабола касается оси);
  - `a < −1`: `−1 < x < 1/a`.
- **Режим провала**: R4 — отказ от обработки параметрического случая.
- **Метод laffie**: M1 + M2 — case-split по знаку `a` (открытость параболы
  + поведение на бесконечности), при `a < 0` дополнительный case-split по
  относительному порядку `1/a` и `−1`. В каждой ветви sympy решает
  конкретное численное неравенство.
- **Источник**: Сканави (параметрические неравенства).
- **Заметка**: квадратичное обобщение C10. Особенно важно, что внутри
  `a < 0` нужен второй уровень case-split — это типичный pattern для
  rule-based engine с вложенной дизъюнкцией.

#### C26 — `Intersection` с `Reals` остаётся невычисленным для `±sqrt(a)`

- **Постановка**: решить относительно `x` уравнение
  `x⁴ − (a + 1)·x² + a = 0`.
- **SymPy**: `solve(...)` → `[−1, 1, −sqrt(a), sqrt(a)]`. `solveset(..., S.Reals)`
  → `Intersection({−1, 1, −sqrt(a), sqrt(a)}, Reals)` — выражение остаётся
  невычисленным, без case-split по знаку `a`. `factor(...)` работает и
  даёт `(x² − a)(x − 1)(x + 1)`.
- **Ожидаемый ответ**: case-split по `a`:
  - `a < 0`: `{−1, 1}` (`x² = a` не имеет вещественных корней);
  - `a = 0`: `{−1, 0, 1}`;
  - `0 < a < 1` или `a > 1`: `{−1, 1, −√a, √a}`;
  - `a = 1`: `{−1, 1}` (двойные корни).
- **Режим провала**: R1 — после факторизации `(x² − 1)(x² − a) = 0` ветвь
  `x² = a` обрабатывается без анализа знака `a`; `Intersection` с `Reals`
  не свёрнут.
- **Метод laffie**: M5 — явная факторизация `(x² − 1)(x² − a)`, далее
  case-split на знак `a` в ветви `x² = a` с применением правила
  «`x² = c` имеет вещественные корни iff `c ≥ 0`». Делегирование sympy в
  каждой ветви с конкретной формой `a`.
- **Источник**: Сканави (биквадратное с параметром).
- **Заметка**: ключевая карточка — заполняет ранее пустую клетку R1×M5.
  Показывает, что `Intersection({...}, Reals)` без знания знака
  параметра — стандартное место провала, где laffie может вмешаться.

#### C12 — лишний корень в логарифмическом уравнении

- **Постановка**: `x · log(x) = 0` относительно `x`.
- **SymPy**: `solve(x*log(x), x)` → `[0, 1]`.
- **Ожидаемый ответ**: `{1}` — корень `x = 0` нарушает ОДЗ
  (`log(0)` не определён).
- **Режим провала**: R2 — лишний корень из-за отсутствия проверки ОДЗ.
- **Метод laffie**: M3 — после получения формальных корней пропустить
  каждый через requirement «`x` входит в область определения исходного
  выражения», в данном случае — `x > 0`.
- **Источник**: SymPy issue [#27062](https://github.com/sympy/sympy/issues/27062).
- **Заметка**: минимальная и каноническая ОДЗ-задача — хороший
  первый пример M3 в публикации.

#### C29 — параметрическое иррациональное: лишний корень при ОДЗ `x ≥ |a|`

- **Постановка**: `√(x − a) + √(x + a) = √(2·x)` относительно `x`.
- **SymPy**: `solve(...)` → `[−a, a]`. `solveset(..., S.Reals)` →
  `{−|a|, |a|}`.
- **Ожидаемый ответ**: `x = |a|` (один корень).
  ОДЗ исходного уравнения в вещественных: `x − a ≥ 0`, `x + a ≥ 0`,
  `2x ≥ 0` → `x ≥ |a|`. После возведения в квадрат получается
  `√(x² − a²) = 0` → `x² = a²`, формально `x = ±|a|`. Но `x = −|a|`
  удовлетворяет ОДЗ только при `a = 0` (тогда оба `±|a|` сливаются в
  единственный корень `0`). Для `a ≠ 0` корень `x = −|a|` лишний.
- **Режим провала**: R2 — лишний корень (`x = −a` или `x = −|a|`)
  не удовлетворяет ОДЗ исходного уравнения.
- **Метод laffie**: M3 — после делегирования формального решения sympy
  применить требование `x ≥ |a|` к каждому корню. Дополнительно M1 для
  обработки знака `a`: правило «`|a| = a` если `a ≥ 0`, иначе `−a`».
- **Источник**: Сканави.
- **Заметка**: дополняет C12 (которое было ОДЗ-проблемой на конечной
  точке `log(0)`) параметрическим случаем. Также пример того, что
  `solveset` хоть и переписывает в `{−|a|, |a|}`, всё равно не делает
  case-split по знаку `a` для отсева корня.

#### C30 — `solve` факторизованного уравнения возвращает корень вне ОДЗ другого множителя

- **Постановка**: `(1 + cos x)·(1 − tg(x/2)) = 0` относительно `x`.
- **SymPy**: `solve(...)` → `[π/2, π]`. `solveset(..., S.Reals)` →
  `Union(ImageSet(λn, 4πn + π/2), ImageSet(λn, 4πn + 5π/2))` (то есть
  только серия `x = π/2 + 2π·k`).
- **Ожидаемый ответ** (строгое прочтение, через ОДЗ выражения): только
  `x = π/2 + 2π·k`. Серия `x = π + 2π·k` от первого множителя совпадает
  с дырой ОДЗ второго (`tg(x/2)` не определён при `x = π + 2π·k`), и в
  исходном выражении эти точки — `0·undefined`, то есть вне области
  определения. Slack-прочтение «один множитель равен нулю → весь
  продукт ноль» допустило бы и эту серию, но `solveset` выбирает
  строгое и оказывается ближе к истине, чем `solve`.
- **Режим провала**: R2 — `solve` возвращает лишний корень `x = π`
  (и всю серию через периодизацию), не учитывая ОДЗ второго множителя.
- **Метод laffie**: M3 — после факторизации и решения каждого
  множителя отдельно, фильтрация по ОДЗ исходного выражения
  (объединение ОДЗ всех множителей). Правило: «корень `x₀` ветви
  `f(x₀) = 0` валиден только если `g(x₀)` определён».
- **Источник**: Сканави.
- **Заметка**: разрыв между `solve` и `solveset` — `solveset`
  оказывается строже к ОДЗ. Ещё один аргумент за делегирование на
  более строгий API. Расширяет R2×M3 третьим случаем (после C12 и
  C29) — теперь покрыта и факторная форма потери ОДЗ.

#### C27 — нет API для «при каких параметрах система имеет решение»

- **Постановка**: при каких значениях параметра `a` система
  `{ x + y = a, x² + y² = a }` имеет вещественное решение?
- **SymPy**: `solve(...)` → `[(a/2 − √(−a(a − 2))/2, a/2 + √(−a(a − 2))/2),
  (a/2 + √(−a(a − 2))/2, a/2 − √(−a(a − 2))/2)]`. Sympy выдаёт формальную
  параметризацию через `√(−a(a − 2))`, не сообщая, что выражение под
  корнем может быть отрицательным. Прямого API «для каких `a` существует
  вещественное решение» нет.
- **Ожидаемый ответ**: `a ∈ [0, 2]` — из условия неотрицательности
  дискриминанта `−a(a − 2) ≥ 0`.
- **Режим провала**: R6 — отсутствие режима «existence as set of parameter
  values». `solveset(−a(a − 2) ≥ 0, a, S.Reals)` корректно возвращает
  `Interval(0, 2)`, но требуется ручная экстракция дискриминанта.
- **Метод laffie**: M1 — после делегирования `solve` извлечь дискриминант
  из подкоренных выражений в ответе, наложить условие `≥ 0`, делегировать
  обратно sympy для решения относительно параметра.
- **Источник**: классическая олимпиадная задача (Москва).
- **Заметка**: заполняет ранее пустую клетку R6×M1. Та же категория
  meta-вопросов «при каких параметрах…», что и ЕГЭ-задание 18 (D3 в
  candidate-секции). В выборку взят один представитель — D3 формально
  относится к тому же классу.

#### C11 — переопределённая система с разрешимой при условии на параметр

- **Постановка**: система `{ x + y = 1, 2·x + 2·y = p }` относительно

- **SymPy**: `solve([x+y-1, 2*x+2*y-p], [x, y])` → `[]` (нет решений в общем).

- **Режим провала**: R4 — пустой ответ при существующем (под условием)

- **Метод laffie**: M1 — обнаружение rank-дефицита системы (вторая строка

- **Источник**: собственная верификация.

### Тир 2 — архитектурные пределы CAS

Failure укоренён в архитектурных выборах sympy: default-домен, principal branch, отсутствие prove-режима, отсутствие constraint-solver, не-пропагация real-домена через Gröbner-pipeline. Без рефакторинга sympy вряд ли исчезнет.

Гибрид может, но pure rule-based laffie часто справится и сам — карточки нужны как «структурные пределы CAS», подкрепляющие тезис, что laffie полезен не временно.

#### C9 — доказательство тождества/неравенства

- **Постановка**: доказать `(a + b)² ≥ 4·a·b` для всех вещественных `a, b`.
- **SymPy**: `simplify((a+b)**2 - 4*a*b)` → `(a+b)² − 4ab` (без сворачивания);
  `ask(Q.nonnegative((a+b)**2 - 4*a*b))` → `None` (не знает).
- **Ожидаемый ответ**: True (`(a+b)² − 4ab = (a−b)² ≥ 0`).
- **Режим провала**: R6 — нет prove-режима.
- **Метод laffie**: M6 — преобразование цели к виду `(a−b)² ≥ 0`, после
  чего знак выводится из правила «квадрат вещественного неотрицателен».
  Это уже непосредственно режим `prove(...)` laffie.
- **Источник**: собственное добавление; категория «prove» из обсуждения
  с пользователем.
- **Заметка**: важная карточка — показывает контраст с SymPy не на
  «laffie + sympy лучше sympy», а на «laffie может то, чего sympy не может
  в принципе».

#### C31 — `solve` системы игнорирует `real=True`, возвращает комплексное семейство

- **Постановка**: найти все вещественные `(x, y, z)`, удовлетворяющие
  системе `{x + y + z = 6, x³ + y³ + z³ = 3·x·y·z}`.
- **SymPy**: при `real=True` для всех символов `solve(...)` и
  `nonlinsolve(...)` возвращают параметрическое семейство с явными
  `√3·I`-членами:
  ```
  (-z/2 − √3·I·z/2 + 3 + √3·I,
   -z/2 + √3·I·(z − 2)/2 + 3,
   z)
  ```
  и сопряжённое. То есть sympy не учитывает декларацию real-домена и
  возвращает полное комплексное многообразие.
- **Ожидаемый ответ**: `(x, y, z) = (2, 2, 2)`. Через тождество
  `x³ + y³ + z³ − 3xyz = (x + y + z)·((x − y)² + (y − z)² + (z − x)²)/2`,
  поскольку `x + y + z = 6 ≠ 0`, второй множитель должен быть равен
  нулю; в вещественных это означает `x = y = z = 2`.
- **Режим провала**: R5 — sympy выдаёт явно комплексные значения для
  вещественных символов. Содержит и R3 (неполное множество в Reals —
  единственное вещественное решение `(2, 2, 2)` не выделяется явно).
- **Метод laffie**: M3 + M5 — явная факторизация по тождеству, разбор
  ветвей `(x + y + z = 0)` vs `((x−y)² + (y−z)² + (x−z)² = 0)`, в
  каждой ветви делегирование sympy с применением правила «сумма
  вещественных квадратов равна нулю iff каждый квадрат равен нулю».
- **Источник**: МГУ вступительные.
- **Заметка**: пример того, что декларация `real=True` не уважается
  внутри `nonlinsolve`/Gröbner-pipeline. Это структурное ограничение,
  а не bug в одной задаче — ту же поломку можно ожидать на любой
  системе, где вещественное решение получается через факторизацию
  «всё ноль ⟺ все слагаемые нули».

#### C5 — предел с действительным кубическим корнем

- **Постановка**: `lim_{x → −8} (x² + 10x + 16) / (12 + 6·x^(1/3))`.
- **SymPy**: `limit(...)` → `0`.
- **Ожидаемый ответ**: `−12`.
- **Режим провала**: R5 — SymPy интерпретирует `x^(1/3)` как принципиальную
  комплексную ветвь, не действительный кубический корень.
- **Метод laffie**: M3 — явная аннотация «`x^(1/3)` понимается как
  действительная функция в этой задаче»; пересчёт предела с этой аннотацией
  и делегирование вычисления sympy на упрощённой форме.
- **Источник**: локальная верификация.
- **Заметка**: пограничная — нужна именно семантическая аннотация, не чисто
  алгебраический case-split. Включена для обсуждения scope:
  попадает ли это в проект или вне.

#### C13 — `solve` навязывает согласование параметров

- **Постановка**: решить относительно `x` систему
  `{ a/b = 5, c/d = 5, a/b − c/d = x }`, где `a, b, c, d` — параметры.
- **SymPy**: `solve([a/b-5, c/d-5, a/b-c/d-x], [x])` →
  `{x: (a·d − b·c)/(b·d)}`.
- **Ожидаемый ответ**: `∅`. Первые два уравнения для общих `a, b, c, d`
  несовместны; решение существует только при `a/b = c/d = 5` — но это
  ограничение на параметры, не на `x`. SymPy неявно принимает
  ограничение и считает его выполненным.
- **Режим провала**: R5 — неверный ответ через неявное предположение
  о значении параметров.
- **Метод laffie**: M1 — явный case-split: ограничения на параметры
  выносятся в условия ответа (`(a/b = 5 ∧ c/d = 5) ⇒ x = a/b − c/d ∨
  иначе ∅`).
- **Источник**: SymPy issue [#24835](https://github.com/sympy/sympy/issues/24835).

#### C20 — `Ne(x, 2).as_set()` неявно принимает `x ∈ ℝ`

- **Постановка**: представить `x ≠ 2` как множество без априорного
  знания типа `x`.
- **SymPy**: `Ne(x, 2).as_set()` →
  `Interval.open(−∞, 2) ∪ Interval.open(2, +∞)`.
- **Ожидаемый ответ**: `Complement(UniversalSet, {2})` —
  поскольку `x` может быть, например, `zoo`, не все элементы
  дополнения вещественны.
- **Режим провала**: R5 — неявное сужение домена до `ℝ`.
- **Метод laffie**: M3 — явное представление ОДЗ как параметра
  представления; `as_set` без знания домена должен возвращать
  general complement, при `x ∈ ℝ` — указанный объединение.
- **Источник**: SymPy issue [#22348](https://github.com/sympy/sympy/issues/22348).

#### C4 — система полиномиальных неравенств с двумя переменными

#### C6 — тригонометрическое уравнение под `solve`

- **Режим провала**: R3 — `solve` возвращает корни на одном периоде, не
  параметризует серию.
- **Метод laffie**: M4 — введение целочисленного параметра. Правило
  «решение `cos(x) = 1` в общем виде есть `x = 2πk, k ∈ ℤ`».
- **Источник**: локальная верификация.
- **Заметка**: `solveset(cos(x)-1, x)` корректно возвращает
  `ImageSet(Lambda(_n, 2π·_n), ℤ)`. То есть failure в `solve`, не в
  SymPy в целом. Это даёт нюансированную карточку — обсудимо.

#### C22 — `solve` теряет вторую ветвь LambertW

- **Постановка**: для CDF `F(y) = (−y − 1)·e^{−y} + 1` решить относительно
  `y` уравнение `F(y) = x` (например, при `x = 0.95`).
- **SymPy**: `solve(Eq(F(y), x), y)` → `[−LambertW((x − 1)·e^{−1}) − 1]`,
  то есть только главная ветвь `W₀`.
- **Ожидаемый ответ**: при `x ∈ ((1 − e^{−1}), 1)` уравнение имеет два
  вещественных корня — `y₀ = −LambertW₀((x − 1)e^{−1}) − 1` и
  `y₋₁ = −LambertW₋₁((x − 1)e^{−1}) − 1`. Численная проверка: при `x = 0.95`
  корни `y ≈ −0.981` и `y ≈ 4.744` (`nsolve` находит оба, `solve` только
  один). `solveset(..., S.Reals)` возвращает `ConditionSet`, то есть тоже
  отказывается дать полный ответ.
- **Режим провала**: R3 — неполное множество корней (выдана только одна
  ветвь многозначной обратной).
- **Метод laffie**: M4 (расширенный — discrete-param) — введение индекса
  ветви `n ∈ {0, −1}` для LambertW в области, где обе вещественные;
  правило «если аргумент `LambertW` в `(−1/e, 0)`, обе вещественные ветви
  дают корни». В каждой ветви sympy вычисляет численно/символьно.
- **Источник**: StackOverflow [#49817984](https://stackoverflow.com/questions/49817984).
- **Заметка**: важное расширение M4 за пределы тригонометрии. Тот же
  rule-based приём (введение целочисленного параметра серии) переносится
  на ветви LambertW и других многозначных функций.

#### C18 — предел `Piecewise` не учитывает направление в граничной точке

- **Постановка**: пусть `p(x) = x²` при `x ≤ 2` и `5x − 7` при `x > 2`.
  Найти `lim_{x → 2+} p(x)`.
- **SymPy**: `limit(p, x, 2, '+')` → `4`.
- **Ожидаемый ответ**: `3` — в правую полуокрестность точки `x = 2`
  попадает только ветвь `5x − 7`, её значение в пределе равно `3`.
- **Режим провала**: R5 — неверный ответ из-за выбора неправильной
  ветви Piecewise при подходе справа.
- **Метод laffie**: M2 — правило выбора ветви Piecewise по направлению
  предела: `lim_{x → a+}` берёт ветвь, активную на `(a, a + ε)`.
- **Источник**: SymPy issue [#26313](https://github.com/sympy/sympy/issues/26313).
- **Заметка**: limits-adjacent — задача про координацию выбора ветви,
  не про CAS-машинерию пределов. Удобный пример того, что даже в чистом
  анализе rule-based может ловить координационные ошибки.

#### C8 — уравнение с суммой модулей

- **Постановка**: `|x − 1| + |x − 3| = 2` относительно `x`.
- **SymPy**: на 1.14.0 `solve(...)` всё ещё бросает `NotImplementedError`
  с сообщением, что `solve` не умеет представлять интервальные решения
  в виде дискретного списка. `solveset(..., S.Reals)` корректно возвращает
  `Interval(1, 3)`.
- **Ожидаемый ответ**: `x ∈ [1, 3]`.
- **Режим провала**: R4 в `solve`. Failure локализован — solveset
  справляется. Аналог C6: рассогласование между `solve` и `solveset`.
- **Метод laffie**: M2 — разбор по знаку каждого выражения под модулем
  (4 случая), отбор согласованных. В двух из четырёх случаев получится
  тождество — laffie должна корректно представить «вся ветвь — решение».
- **Источник**: локальная верификация.
- **Заметка**: интересна тем, что ответ — не дискретное множество, а
  отрезок. Хороший тест на способность laffie возвращать интервальные
  ответы из case-split. Также карточка-аргумент за делегирование на уровне
  более универсального solveset, а не legacy solve.

#### C16 — линейное модулярное уравнение

- **Постановка**: `192 · i₀ ≡ 0 (mod 2304)` относительно целого `i₀`.
- **SymPy**: `solve(Eq(Mod(192*i0, 2304), 0), i0)` →
  `NotImplementedError`. `solveset(..., Integers)` →
  `ImageSet(Lambda(_n, 12·_n), ℤ)`.
- **Ожидаемый ответ**: `i₀ ≡ 0 (mod 12)`, то есть `i₀ ∈ 12·ℤ`.
- **Режим провала**: R4 — `solve` не справляется; `solveset` справляется,
  но возвращает `ImageSet`, неудобный для дальнейшей работы.
- **Метод laffie**: M5 — приведение `(a · n) ≡ 0 (mod m) ⇔ n ≡ 0 (mod m/gcd(a,m))`
  как явное правило сокращения; ответ как `n ∈ k·ℤ`.
- **Источник**: SymPy issue [#25883](https://github.com/sympy/sympy/issues/25883).

#### C19 — предел с `|sqrt(x²−1)|` теряет знак

- **Постановка**: `lim_{x → 1−} x / |sqrt(x² − 1)|` и
  `lim_{x → −1+} x / |sqrt(x² − 1)|`.
- **SymPy**: оба возвращают значения с неверным знаком
  (на `1−` возвращает `−∞` вместо `+∞`; на `−1+` возвращает `+∞`
  вместо `−∞`).
- **Ожидаемый ответ**: оба должны быть с правильными знаками
  по знаку `x` в окрестности.
- **Режим провала**: R5 — неверный знак из-за ошибки отслеживания
  знака `x` при подходе к точке.
- **Метод laffie**: M2 — явное отслеживание знака переменной в
  малой окрестности предельной точки.
- **Источник**: SymPy issue [#25681](https://github.com/sympy/sympy/issues/25681).
- **Заметка**: limits-adjacent. Хороший контрпример к мнению, что
  пределы — исключительно «чистый CAS».

#### C7 — уравнение с модулем (перенесена в Audit)

На SymPy 1.14.0 `solve(Eq(Abs(x**2 − 4·x + 3), x − 1), x)` корректно
возвращает `[1, 2, 4]`. При ревизии обнаружено, что заявленный ожидаемый
ответ `{2, 1 + √3, …}` был с ошибкой — численная подстановка показывает,
что `1 + √3` не корень. Реальные корни: `{1, 2, 4}` (sympy совпадает
с разбором случаев). Подробности — в секции «Audit обновлений SymPy».
Карточка сохраняет номер для traceability и может использоваться как
контрольная (чтобы laffie не регрессировал относительно sympy).

## Audit обновлений SymPy

При сравнении user-reported failures и candidate-задач с поведением
текущей 1.14.0 регулярно обнаруживаются примеры, где sympy уже
справляется. Эти случаи в C-каталог не идут, но мигрируют сюда — как
эмпирический сигнал «версия имеет значение» и как пул контрольных задач,
на которых laffie не должен регрессировать относительно sympy.

Уже работает на 1.14.0 (на момент верификации не воспроизводится):

**Из StackOverflow (10 кандидатов, 5 fixed):**

- SO #79113424 — `limit(atan((1−x)/(x+3)), x, −∞)` → `−π/4` (было `nan`).
- SO #33923802 — `simplify(Abs(exp(I·t·…/ℏ)))` → `1` (было `Abs(...)`).
- SO #24062112 — `simplify(Abs(exp(I)))` → `1` (то же).
- SO #16096164 — `solve(num/denom = p)` корректно возвращает все три корня
  `[0, 1, (Waa − WAa)/(2WAa − WAA − Waa)]`.
- SO #69608662 — `linsolve` возвращает корректное параметрическое решение
  системы 8×8.

**Из задачников (M2-пачка D18–D20):**

- D18 (Виленкин/Мордкович): `solve(|x − 1| + |x + 2| = 5)` →
  `[−3, 2]` корректно. Двойной модуль с дискретным ответом теперь
  работает напрямую.
- D19 (региональная олимпиада): `solve(||x − 2| − 3| = 1)` →
  `[−2, 0, 4, 6]` корректно. Вложенный модуль также раскручивается
  без вмешательства.

**Из задачников (M3-пачка D13–D17):**

- D13 (Сканави): `solve(√(x + 3) − √(x − 1) = 1)` → `[13/4]` корректно.
  Иррациональное уравнение со стандартным возведением в квадрат теперь
  решается напрямую.
- D16 (Виленкин): `solve((x² − 9)/(x − 3) = 6)` → `[]` (∅) корректно.
  ОДЗ-исключение точки сокращения соблюдено.
- D17 (Сканави): `reduce_inequalities([log_x(x²−2x) > 1], [x])` →
  `3 < x` корректно. Логарифмическое неравенство с переменным основанием
  обрабатывается с правильным case-split по основанию.

**Из задачников (M5-пачка D21–D22):**

- D21 (Сканави, симметричная `{x+y+xy=11, x²y+xy²=30}`): `solve` и
  `nonlinsolve` дают полный набор `{(1,5), (2,3), (3,2), (5,1)}`.
  Симметрия раскручивается без вмешательства.
- D22 (Сканави, однородная `{x²−3xy+2y²=0, x²+y²=10}`): `solve` и
  `nonlinsolve` дают `{(±√5, ±√5), (±2√2, ±√2)}`. Факторизация первой
  формы и подстановка во вторую происходят автоматически.

Реальные провалы по M5 в каталоге (C3, C14, C16) приходят из issue
трекера sympy, не из задачников — что согласуется с этим наблюдением.

**Из задачников (D23–D29: олимпиадные + Демидович):**

- D23 (Всероссийская, `x = √(2 − √(2 + x))`): `solve` корректно отбирает
  единственный вещественный корень `−1/2 + √5/2` ≈ 0.618 из четырёх
  формальных корней получающейся биквадратики, фильтруя по ОДЗ.
  Впечатляющая работа с вложенным радикалом.
- D24 (Putnam-style, Φ₁₄(x) = 0 в ℝ): `solveset(..., S.Reals)` →
  `EmptySet`; `solveset(..., S.Complexes)` → 6 примитивных корней 14-й
  степени из единицы, выраженных через `cos`/`sin`.
- D28 (Демидович, `√(x + 2) > x`): `solveset` → `Interval.Ropen(−2, 2)`;
  `reduce_inequalities` → `(−2 ≤ x) ∧ (x < 2)`. Корректно.
- D29 (ЕГЭ-14, `(x²−5x+6)/(x²−4) ≥ 0`): `solveset` →
  `Union(Interval.open(−∞, −2), Interval(3, ∞))`. Правильно учтена дыра
  ОДЗ при сокращении.

**Из задачников (M4-пачка D8–D12):**

В M4-пачке наблюдается стабильный паттерн «`solve` теряет периодичность,
`solveset` возвращает Union серий корректно». Это в точности тот же
failure-механизм, что в C6 (`cos(x) − 1 = 0`); вместо отдельных карточек
эти случаи отнесены к audit как иллюстрации повторяемости C6:

- D8 (Мордкович/Демидович, `sin 3x = sin x`): `solve` → 5 точечных
  корней, `solveset` → корректный Union из 6 ImageSet (объединяет в
  серии `x = π·k` и `x = π/4 + π·k/2`).
- D9 (Демидович, `sin x · cos 2x = 0`): `solve` → 4 точечных,
  `solveset` корректно возвращает Union серий.
- D10 (Сканави, `tg x + ctg x = 2`): `solve` → `[π/4]` (только база),
  `solveset` корректно даёт `{2πn + π/4} ∪ {2πn + 5π/4} = {π/4 + π·k}`.
- D11 (ЕГЭ-13, `2 sin²x + sin 2x = 0` на `[−π, π]`): `solve` возвращает
  `[0, −π/4, 3π/4]`, теряя граничные `±π`. `solveset(..., Interval(−π, π))`
  даёт полный набор `{−π, −π/4, 0, 3π/4, π}`. Усиленная иллюстрация
  C6-паттерна на bounded-интервале.

**Бывшие C-карточки, переставшие воспроизводиться:**

- C7 (модуль с правой частью, `|x² − 4·x + 3| = x − 1`): `solve` теперь
  возвращает `[1, 2, 4]`. Дополнительно при ревизии оказалось, что
  заявленный ожидаемый ответ был с ошибкой (1 + √3 не является корнем).
  Карточка сохранена в каталоге как redirect-stub под прежним номером.
  Освобождает клетку R4×M3.

C-карточка C8 (`|x − 1| + |x − 3| = 2`) частично починилась: `solve` всё
ещё бросает `NotImplementedError` про интервал, но `solveset` теперь
корректно возвращает `Interval(1, 3)`. Карточка осталась в каталоге с
обновлённым описанием failure-mode (теперь это «несоответствие между
solve и solveset», как в C6).

Регулярная регрессия каталога при апгрейде SymPy — отдельный пункт
backlog.

## Candidate карточки (требуют верификации на SymPy 1.14.0)

Подобраны фоновым агентом из:

- Сканави «Сборник задач для поступающих в вузы»
- Виленкин (углублённые курсы алгебры 8–9 классов)
- Мордкович (углублённый курс алгебры старших классов)
- Демидович «Сборник задач по математическому анализу»
- ЕГЭ — задания части 2 (13–19 в текущей нумерации)
- Российские олимпиады разных уровней
- Putnam, IMO

Все источники — из knowledge cutoff агента. Перед включением в основную часть
каталога каждая карточка должна быть верифицирована — нужно убедиться, что
SymPy 1.14.0 действительно проигрывает на ней, и что описанный режим провала
актуален.

Список ниже — пул кандидатов в порядке убывания ожидаемой ценности по оценке
агента. Полные формулировки с источниками вынесены в отдельный документ при
расширении каталога; здесь — компактный обзор.

### Параметрические уравнения и неравенства (M1) — пачка верифицирована

Из M1-пачки в verified-каталог переведены:

- D1 → **C24** (R1×M1, две вырожденные ветви параметра).
- D2 → **C25** (R4×M1+M2, отказ `reduce_inequalities`).
- D5 → **C27** (R6×M1, нет API «при каких параметрах разрешимо»).
- D7 → **C26** (R1×M5, `Intersection({±√a}, ℝ)` без свёртки).

Не переведены (с обоснованиями):

- D3. «При каких `a` уравнение `|x² − 4x + 3| = a` имеет ровно три корня?»
  (ЕГЭ задание 18) — meta-вопрос «при каких параметрах ровно N корней» того
  же класса R6, что и D5/C27. Включена в C27 в заметке как
  представительный случай. Самостоятельной карточки не получает, чтобы не
  раздувать R6×M1 повторами.
- D4. `log_a(x² − 1) = log_a(2x + 2)` (Сканави) — на 1.14.0 поведение
  непостоянное: `solve` без assumptions возвращает `[3]` (отфильтровал
  ОДЗ); `solve` с `x` real возвращает `[]` (потерял всё). Чистого
  failure-режима под одной формулировкой нет; перенести в R3-batch при
  ОДЗ-аудите (см. ниже M3).
- D6. «При каких `a` `sin x + cos x = a` имеет решение на `[0, π]`?»
  (Демидович, Виленкин) — `solve` даёт Weierstrass без периода и без
  условия `2 − a² ≥ 0`; `solveset` отвечает `ConditionSet`; зато
  `minimum/maximum` на интервале корректно дают `(−1, √2)`. Близка к C6
  и тематически перекрывается с C27. Откладывается до решения, нужна ли
  отдельная карточка «параметрическая тригонометрия на интервале».

  и Complexes).
- D25 (IMO 1959 №1, `gcd(21n + 4, 14n + 3) = 1`) → borderline. `sp.gcd`
  как полиномиальный gcd возвращает `1`, что (через Bezout-комбинацию
  `3·(14n+3) − 2·(21n+4) = 1`) формально достаточно для доказательства,
  но sympy не выдаёт это как «proof object». Тот же класс R6 (нет
  prove-режима), но с частичным workaround — карточка не оформлена,
  чтобы не дублировать C9.
- D26 (МГУ вступительные) → **C31** (R5×M3+M5, sympy игнорирует
  `real=True` и возвращает комплексное параметрическое семейство).
- D27 (Демидович, `√(x² − 4)/(x − 2)`) → borderline. `simplify` без
  assumptions возвращает выражение неизменным; sign-aware
  piecewise-упрощение требует case-split по `x ≷ ±2`. Не оформлено
  как карточка из-за soft-failure режима (sympy ничего не утверждает
  неверно — просто не упрощает).
- D28 (Демидович) → Audit.
- D29 (ЕГЭ-14) → Audit.

## Outline публикации (черновик для обсуждения)

Заголовок (рабочий): «Гибридное решение алгебраических задач: rule-based
координация и CAS-делегирование».

Структура:

1. **Введение** — позиционирование. Современные CAS (SymPy как пример)
   сильны в чистой алгебраической манипуляции, но систематически теряют
   решения в задачах, требующих координации ветвлений: разбора случаев
   по параметрам, отслеживания ОДЗ, факторизации до запуска тяжёлой
   машинерии. Аналогично, чистые rule-based системы плохо масштабируются
   на тяжёлую алгебраическую арифметику.
2. **Контекст и связанные работы** — `nlinarith`/`omega` в Coq, Sledgehammer
   в Isabelle, `polyrith`/`ring` в Lean: тактическое делегирование как
   архитектурный приём. Школьная и абитуриентская алгебра как класс,
   где такой приём почти не применялся.
3. **Архитектура** — laffie как координатор: rule-based pattern matching,
   bidirectional search, явное представление дизъюнкции в ответе. SymPy как
   оракул через PyO3-bridge. Procedural symbol как граница доверия.
4. **Каталог провалов SymPy** — таксономия (R1–R6 × M1–M6) на основе
   данного документа. Эмпирические результаты на SymPy 1.14.0.
5. **Эксперименты** — для каждой карточки: SymPy-результат, laffie+SymPy
   результат, метрика полноты ответа.
6. **Обсуждение и ограничения** — где гибрид принципиально не применим
   (Гребнер на полных системах без факторизации, RootOf-арифметика,
   Risch-интегрирование).
7. **Заключение** — основная новизна: систематическая таксономия
   координационных провалов CAS + воспроизводимый набор задач +
   архитектурный паттерн делегирования для школьно-абитуриентской алгебры.

Открытые вопросы:

- Целевая publication venue (тезисы конференции, статья в журнал, препринт).
- Размер итогового набора задач (15? 30? 50?).
- Включать ли prove-режим как отдельную секцию или как часть таксономии.
- Нужны ли количественные метрики (доля верных ответов, время) или
  достаточно качественной классификации.

## Методология верификации

Для каждой verified-карточки:

1. Минимальный воспроизводимый код на SymPy с фиксированной версией.
2. Точная формулировка ожидаемого ответа (со ссылкой на источник или
   доказательством).
3. Категоризация по таксономии R × M.
4. Эскиз rule-based подхода — на уровне «какие правила нужны», без полного
   `.sym` кода (полный код — фаза engineering PoC).

Для перевода candidate-карточек в verified:

1. Прогон через текущую SymPy.
2. Если SymPy справляется — карточка отбрасывается или ставится в раздел
   «контрольных» (для проверки, что laffie не регрессирует относительно
   sympy).
3. Если SymPy проигрывает — фиксация конкретного режима провала.
