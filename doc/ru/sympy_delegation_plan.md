## План: гибридное решение задач через делегирование SymPy

### Контекст

Многие классы задач, на которых SymPy теряет решения или возвращает неполный
ответ, проблемны не из-за неумения считать, а из-за отсутствия координации
ветвлений: разбора случаев по параметрам, отслеживания ОДЗ, факторизации до
запуска тяжёлой машинерии. Laffie умеет именно координацию через rule-based
рассуждение. SymPy умеет считать. Гибрид: laffie разбирает случаи и сводит
задачу к чистой алгебре, SymPy решает каждую ветвь, laffie собирает ответ.

Аналог в proof assistants — тактики `nlinarith`/`omega`/Sledgehammer, которые
делегируют тяжёлую арифметику в SMT/CAS. В области школьной и абитуриентской
алгебры с явным разбором случаев такой подход почти не исследован — это даёт
направлению научную новизну.

### Текущий приоритет

Подготовка артефактов под внешнее обсуждение. Ценный артефакт сейчас —
**каталог задач + черновик публикации**, не PoC-код. Сам каталог живёт в
[sympy_catalog.md](sympy_catalog.md); этот документ — план работы более
высокого уровня.

### Этапы

#### Phase 0 (текущая) — Каталог и outline публикации

Цель — собрать 10–15 верифицированных глубоких карточек задач, на которых
SymPy объективно проигрывает, классифицировать их в таксономии «провал ×
метод rule-based», очертить scope публикации.

Артефакт: [sympy_catalog.md](sympy_catalog.md).

Состояние: 31 verified карточка на SymPy 1.14.0 (источники: GitHub issues,
StackOverflow, локальная верификация, конверсия всех 29 candidate-карточек
из задачников). В ходе ревизии одна старая карточка (C7) перенесена в
audit как «уже работает». 18 textbook-задач + 5 SO-задач = 23 audit-кейса.
Все candidate-пачки пройдены. Готово для внешнего обсуждения.

Дальнейшая работа в фазе 0 (после внешней обратной связи):

1. Уточнение outline под выбранное направление.
2. Возможное расширение или сужение каталога.
3. math.SE и issue trackers других CAS как дополнительные источники, если
   потребуется расширение выборки.

#### Phase 1 — Engineering PoC

Запускается **только** после согласования scope. Не ранее.

Цель — показать end-to-end сценарий «laffie разбирает случаи → sympy решает →
laffie валидирует → laffie собирает ответ» на одной задаче-эталоне из
каталога. Кандидат-эталон по умолчанию: карточка C1 из каталога (`a*x = a`).

Архитектурный паттерн уже проработан: procedural symbol с PyO3-вызовом
sympy + declarative rule с case-split через `||` (по образцу
`rational_roots.md`). Никаких изменений в крейтах `solver`/`parser` не
требуется — вся работа в `symbols/`, `tasks/`, `symbols/py/`.

Поставка PoC:

1. Symbol `sympy_solve(eq, x)` в `symbols/sympy_solve.sym` — обёртка
   `sympy.solve` для конкретного уравнения и переменной, возвращает
   `set(...)` решений или пусто.
2. Расширение `symbols/py/sympy_convert.py` для символа `==`.
3. Правило для линейного `a*x = b` с case-split в новом `.sym` файле.
4. Тест-задача в `tasks/sympy_comparison/parametric/`.
5. Запись результата в таблицу сравнения.

Критерии приёмки PoC:

- `cargo test --workspace` проходит.
- На задаче-эталоне laffie находит оба случая (`a == 0` и `a != 0, x == 1`),
  чистый sympy — только `[1]`.

#### Phase 2 — Параметрические квадратные

Запускается только если PoC показал работающий паттерн и обнаружились
конкретные пробелы, по которым понятно расширение. Без сигнала от Phase 1
не стартует — принцип «defer follow-ups until usage signal».

Кандидат-эталон: карточка C2 (`(a²-1)x²+2(a-1)x+1 = 0`).

#### Phase 3 — Расширение по таксономии

Открытый список, набирается по приоритету в зависимости от внешней обратной
связи, реальной usage pain после Phase 1–2 и ясности направления публикации. Кандидаты в порядке убывания ожидаемой ценности (по таксономии
из каталога):

1. ОДЗ при иррациональных и логарифмических уравнениях.
2. Уравнения с модулем — разбор по знаку.
3. Тригонометрия с целочисленными параметрами (требует символа `k ∈ ℤ`).
4. Системы Гребнера через предварительную факторизацию.
5. Параметрические неравенства с разворотом по знаку.

### Backlog (фиксируем сейчас, не делаем)

- Долгоживущий Python-процесс с warm cache. Сейчас PyO3 attach каждый раз
  заново; для PoC некритично.
- Кэш sympy-вызовов на нормализованной форме запроса.
- Sandbox/timeout вокруг `Python::attach` — для PoC sympy сам разрулит или
  бросит exception.
- Расширение `claude_docs/` английским описанием Python integration.
- `requirements.txt` с pinned sympy — добавить, как только разные ответы
  sympy между версиями реально начнут влиять на результат.
- Web-mining SymPy issues и StackExchange — требует разрешений на WebFetch
  или `gh` CLI.

### Открытые вопросы (для уточнения в Phase 1)

1. Как laffie сейчас выражает «x ∈ ℝ» в ответе? Влияет на формулировку
   ответа в случае `a == 0 && b == 0`.
2. Как формулируется задача `find(x)` с параметром: `a` остаётся свободным
   параметром или фиксируется заранее? От ответа зависит синтаксис `.pbl`.
3. Поведение solver, если правило возвращает дизъюнкцию через `||` и одна
   из ветвей — пустое множество.

Эти вопросы прорабатываются в начале Phase 1 при первой попытке написать
правило.
