# Терминология

Этот документ собирает основные понятия системы и фиксирует терминологию,
используемую в остальной документации. Большая часть терминов привязана к
конкретным типам в коде — соответствия указаны рядом с определениями.

## Терм

**Терм** — корректная формула в индуктивном смысле:

1. Числовые константы и идентификаторы (переменные, параметры) — это термы.
2. Если `f` — `n`-арный функциональный символ, а `t₁, …, tₙ` — термы, то
   `f(t₁, …, tₙ)` — также терм.

В коде терм представлен в виде дерева, где каждый узел — атом одного из
типов (`solver::term::atom::Atom`):

| Атом | Назначение |
|------|------------|
| `Symbol` | Функциональный символ (см. ниже). |
| `Number(Decimal)` | Числовая константа (рациональные представляются дробью). |
| `Variable` | Переменная — обозначает неизвестное в задаче. |
| `Param` | Параметр — заполнитель в шаблоне правила. |
| `ArgList` | Метка вариативного списка аргументов (`..`). |

Хранение и доступ:

- `TermBuf` — собственное дерево терма (`solver::term::buffer`).
- `SharedTerm` — `Arc<TermBuf>` для разделяемого владения.
- `TermRef` / `TermMut` — представления для чтения / записи.

### Функциональный символ

**Функциональный символ** — `n`-арный оператор предметной области (например,
`+`, `*`, `==`, `set`, `sqrt`). Каждый символ описан как `SymbolProgram`
(`solver::term::symbol::program`) и хранит:

- атрибуты (инфиксность, ассоциативность, коммутативность);
- порядок сравнения аргументов;
- калькулятор (вычисляющую процедуру);
- проверку истинности.

Иррациональные числа представляются как термы (`sqrt(2)`); широко
используемые константы (`pi`, `e`, `empty_set`) — как 0-арные символы.

### Переменная и параметр

Идентификаторы делятся на два класса в зависимости от роли:

- **Переменная (`Variable`)** используется в условиях и выводимых термах
  задачи. Это то, что предлагается найти или выразить.
- **Параметр (`Param`)** используется в шаблоне правила. При применении
  правила параметры связываются с подтермами обрабатываемого терма.

Все идентификаторы конкретного терма принадлежат одному из этих классов.

## Задача

**Задача** — пара «целевая установка + список условий».

- **Целевая установка** определяет тип задачи и интересующий терм.
- **Условия** — конечный набор термов, считающихся истинными.

В коде задача — `solver::task::Task`. Целевая установка —
`solver::task::Goal`.

### Типы целевых установок

| Целевая установка | Смысл |
|-------------------|-------|
| `find(x)` | Описать значение неизвестного `x` через известные термы. |
| `find(x, y, …)` | Многомерный поиск: связать каждое неизвестное. |
| `prove(s)` | Вывести терм `s` из условий задачи. |
| `transform(s)` | Преобразовать (обычно — упростить) терм. |

Многомерный `find` (multi-var find) реализуется через
`FindGoal { targets, term }`. Правила с шаблоном `goal(find(x, ..))`
матчат любую форму, содержащую `x` среди целевых переменных.

### Ожидаемый ответ

В файле задачи можно указать ключевое слово `answer` — ожидаемый ответ.
Система не использует его при решении; он сверяется в конце процедуры.
Накопленная база задач выступает в роли набора интеграционных тестов.

## Правило

**Правило** имеет вид «**шаблон ⇒ вывод**» с дополнительным списком
ограничений на параметры.

| Часть | Описание |
|-------|----------|
| Шаблон (`pattern`) | Терм с параметрами. |
| Вывод (`resolution`) | Терм, в который превращается шаблон при применении. |
| Ограничения (`requirements`) | Список термов-условий, которые должны быть истинными. |
| Атрибуты (`attrs`) | Уровень, целевая установка, идентификатор и т. д. (см. [Синтаксис правил](rule_syntax.md)). |

Правило в коде — `solver::rule::Rule`. Применение к терму описано трейтом
`ApplyRule`.

### Применение правила

Алгоритм применения правила `r` к терму `t`:

1. **Унификация.** Найти подстановку параметров, превращающую шаблон `r`
   в подтерм `t₁` обрабатываемого терма `t`.
2. **Проверка ограничений.** Если для найденной подстановки хотя бы одно
   ограничение не выполнено, перейти к следующей подстановке.
3. **Замена.** В `t` заменить `t₁` на терм, полученный из вывода `r`
   применением подстановки.

Возможна неоднозначность: для одной подстановки может быть несколько
вхождений шаблона; и сами подходящие подстановки могут быть не
единственными. Поэтому результатом применения правила к терму считается
множество (возможно пустое) термов.

### Гипотеза и конкретизация

После шага 1 формируется **гипотеза**: пара «вывод правила + ограничения»
с применённой частичной подстановкой. Если в ней остались несвязанные
параметры (например, появившиеся только в ограничениях), гипотеза
**конкретизируется** — параметры доназначаются итеративным связыванием
через `==` и перебором генераторов вида `param in set(…)`.

| Понятие | Тип | См. |
|---------|-----|-----|
| Гипотеза со свободными параметрами | `Hypothesis` | [hypothesis.md](hypothesis.md) |
| Конкретизированная гипотеза | `GroundedHypothesis` | |
| Конкретизация | `Hypothesis::ground()` | |

В литературе соответствует терминам *non-ground clause* / *ground instance* /
*grounding* (instantiation, означивание).

### Обучение системы

**Обучением** называется добавление в систему новых правил или изменение
существующих. Цель — расширить класс решаемых задач или сократить время
решения. Ядро системы при этом не меняется.

## Уровни и переключение внимания

При решении задачи система обходит термы не в глубину и не в ширину, а
**ранжируя по уровню**:

- Каждому правилу `r` приписан **уровень правила** `Lᵣ` (`Rule::level`).
- Каждому терму `t` приписан **уровень терма** `Lₜ` (`TermFilters::level`).
- Новый терм получает `Lₜ = 0`.
- К терму `t` применяются только правила с `Lᵣ = Lₜ`.
- Если ни одно правило этого уровня не дало нового терма, `Lₜ` увеличивается
  на единицу.
- В каждой итерации выбирается активный терм с минимальным `Lₜ`; при
  равенстве — полученный раньше.

Если все активные термы превысили максимальный уровень правил
(`RulesEngine::max_level`), цикл завершается.

Подробнее — [Принцип работы](work_principle.md).

## Метаданные терма

Каждый терм в системе сопровождается метаданными — структурой
`TermProps` (`solver::task::props::TermProps`). Ключевые поля:

| Поле | Что хранит |
|------|------------|
| `id` | Сквозной идентификатор внутри решения. |
| `term: SharedTerm` | Сам терм. |
| `inference: TermInference` | Источник вывода (см. ниже). |
| `filters: TermFilters` | Уровень, кэш символов, фильтры правил, флаги состояния. |
| `rule: TermAsRule` | Лениво построенное правило-подстановка из этого терма. |

Поля `TermFilters` (`solver::rule::term_filters`):

| Поле | Что хранит |
|------|------------|
| `level` | Текущий уровень терма `Lₜ`. |
| `symbols` | Множество функциональных символов терма (для быстрого отбора правил). |
| `applied_rules` | Идентификаторы правил, уже применявшихся к терму. |
| `blocked_rules` | Идентификаторы правил, заблокированных для этого терма. |
| `flags` | Флаги состояния (см. ниже). |

### Флаги состояния

Флаги — биты типа `TermFlags`:

| Флаг | Значение |
|------|----------|
| `REPLACED` | Терм исключён из множества активных (после применения правила с атрибутом `replace` или после упрощения через подзадачу `Transform`). |
| `SIMPLIFIED` | Терм уже был обработан подзадачей упрощения (повторно не обрабатывается). |
| `GOAL` | Терм является альтернативной целевой установкой (получен преобразованием цели). |

Множество **активных** термов — это термы без флага `REPLACED`.

### Источник вывода

`TermInference` указывает, как был получен терм:

| Вариант | Когда |
|---------|-------|
| `Condition` | Терм пришёл из условий задачи (или цели — формально цель тоже считается условием). |
| `Rule { rule, params, parent, requirements }` | Терм получен применением правила `rule` к терму `parent` с подстановкой `params`; `requirements` — доказательства всех проверенных ограничений. |
| `Transform { parent, solution }` | Терм получен упрощением `parent` через подзадачу `Transform`; `solution` — её результат. |

Источник вывода непосредственно не влияет на применение правил, но
позволяет:

- восстановить полную цепочку рассуждений по завершении задачи;
- диагностировать пробелы в базе правил;
- проводить апостериорную проверку корректности.

## Иммутабельность и замена

Термы в системе **иммутабельны**: применение правила не изменяет исходный
терм, а добавляет новый. Метаданные при этом меняются (флаги, фильтры,
уровень).

Чтобы избежать комбинаторного взрыва промежуточных форм при упрощении,
правила могут иметь атрибут `replace` (см. [Синтаксис правил](rule_syntax.md)).
Если такое правило успешно применилось к `t`, исходный `t` помечается
флагом `REPLACED` и больше не выбирается основным циклом — фактически
происходит замена.

## Известное (`known`)

**«Известный»** — статус терма, означающий, что его значение можно считать
определённым. Изначально известны числовые константы; в условиях задачи
можно объявить переменную параметром (`t is known`) — тогда она тоже
считается известной.

Концепция используется:

- в усмотрении ответа: для `find(x)` ответ найден, если получен терм
  `x == v` или `x in A`, где `v` (или `A`) известно;
- в ограничениях правил: типичная запись `b is known`.

Проверка известности производится через подзадачу `prove(t is known)`.
Большая часть выводов — арифметические правила вида «сумма / произведение
известных есть известное».

## Нормализация и упрощение

**Нормализация** — синтаксическое приведение терма к канонической форме
без изменения семантики: раскрытие вложенности ассоциативных операций,
упорядочивание аргументов коммутативных, вычисление константных
выражений, приведение подобных. Реализуется на уровне ядра (`TermMut::normalize`)
и не меняется в процессе обучения.

**Упрощение** — семантически более широкое преобразование, реализуемое
правилами через подзадачу `Transform`: например, вычисление производной
или раскрытие скобок по формуле. Корректность гарантируется правилами,
введёнными в систему.

Уровни нормализации описаны в [normalization.md](normalization.md).

## Подзадача

**Подзадача** — вспомогательная задача, решаемая независимо ради
получения результата для основной. Используется для упрощения термов
(`Transform`), доказательства ограничений правила (`Prove`) и иногда —
для рассмотрения случаев (`Find`).

Подзадачи могут вкладываться (с лимитом `MAX_SUBTASK_LEVEL = 10`) и
кэшируются. Подробнее — [subtasks.md](subtasks.md).

## База правил

**База правил** (`RulesEngine`) — структура, эффективно отбирающая правила,
применимые к данному терму. Двухуровневая: сначала по уровню `Lᵣ`, затем
по функциональному символу шаблона. Подробнее — [rule_base.md](rule_base.md).
