# Принцип работы

Описание того, как ядро системы решает задачу. Документ опирается на
определения из [terminology.md](terminology.md). Конкретные структуры
данных приведены в [code_structure.md](code_structure.md).

## Идея

Система получает на вход задачу — целевую установку и список условий —
и пытается на основе условий вывести терм, удовлетворяющий целевой
установке. Вывод производится **применением правил преобразования** к
ранее полученным термам.

Сложность в порядке обхода: классические DFS/BFS зацикливаются на
одних термах, не доходя до других. Поэтому система использует
**ранжирование правил по уровням**, а порядок обработки термов выбирает
по их собственному (растущему) уровню.

## Переключение внимания

Каждому правилу `r` приписан целочисленный **уровень правила** `Lᵣ`.
Каждому терму `t` — **уровень терма** `Lₜ`. Новый терм рождается с
`Lₜ = 0`. К терму `t` применяются только правила с `Lᵣ = Lₜ`. Если ни
одно правило этого уровня не дало нового терма, `Lₜ` увеличивается на
единицу.

В каждой итерации цикла выбирается активный терм с минимальным `Lₜ`;
при равенстве — добавленный раньше. Когда все активные термы превысили
максимальный уровень правил, цикл завершается без ответа.

Идея уровней — управлять «общеупотребимостью»: правило, ускоряющее
большинство задач, ставится на уровень 0 и применяется первым; узко
специальное — на уровень повыше и подключается, лишь когда базовые
приёмы не сработали.

## Инициализация

До запуска основного цикла система переводит задачу во внутреннее
представление:

1. **Условия.** Каждое условие нормализуется (см. [normalization.md](normalization.md))
   и оформляется в `TermProps` с `inference = Condition`,
   `level = 0`, пустыми списками применённых и заблокированных правил.
2. **Целевая установка.** Из неё извлекается терм-цель и оформляется
   аналогично условию, но с дополнительным флагом `GOAL` в `TermFilters`.
   Это позволяет отдельно отслеживать преобразования цели и не путать
   их с выведенными утверждениями.
3. **Кэш подзадач.** Создаётся пустой кэш для будущих вызовов
   `Transform` / `Prove` / `Find` (см. [subtasks.md](subtasks.md)).
4. **Известные термы.** Для целей вида `find(x, …)` имена `x, …`
   запоминаются как «неизвестные» — это влияет на ранний отказ при
   проверке `t is known`.

## Основной цикл

Цикл крутится до одного из условий завершения: найден ответ, исчерпан
лимит итераций (`EXECUTION_DEADLINE_DEFAULT = 100 000`), некого выбрать,
все термы превысили максимальный уровень. Каждая итерация:

1. **Выбор терма.** Из множества активных термов (с `inference.is_proven()`
   и без флага `REPLACED`) берётся терм с минимальным уровнем.
   Если его уровень превысил `max_level + 1` — выход с
   `NoSolutionsFound`. Реализация: `Solver::try_focus_term`,
   `Solution::pick_next`.
2. **Упрощение.** Если терм ещё не помечен `SIMPLIFIED` и цель задачи —
   не `Transform`, запускается подзадача `Transform(t)`. Если она
   нашла отличный от `t` результат `t'`, исходный `t` помечается
   `REPLACED`, в множество добавляется `t'` (с `SIMPLIFIED`,
   `inference = Transform { parent: t, … }`), итерация переходит к
   следующему циклу. Иначе `t` помечается `SIMPLIFIED`. Реализация:
   `Solver::try_simplify`.
3. **Усмотрение ответа.** Терм проверяется на «является ответом»
   процедурой, зависящей от типа целевой установки (см. ниже). Если
   ответ найден — цикл завершается успешно. Реализация:
   `Solver::check_if_answer`.
4. **Регистрация терма как локального правила.** Из терма строится
   правило-подстановка (если терм имеет вид, пригодный для замены) и
   добавляется в `local_rules` — оно будет применяться к другим термам
   на повышенных уровнях. Это реализует механизм терм-подстановки.
   Реализация: `Solver::add_local_rule` + `TermProps::rule`.
5. **Подбор правил и применение.** Подходящие правила собираются
   через [базу правил](rule_base.md) и применяются к терму до первого,
   породившего новый, обоснованный терм. Если ни одно не сработало,
   уровень терма повышается на единицу. Реализация:
   `Solver::try_infer_new_terms`, `Solver::suggest_rules`,
   `Solver::produce`.

```
loop:
    cycle_counter += 1
    t = pick(active terms by min level)
    if level(t) > max_level: stop "no solutions"
    if !simplified(t) and goal != Transform:
        t' = transform_subtask(t)
        if t' != t: replace t with t', restart loop
        else: mark simplified
    if is_answer(t): stop "found"
    register t as local rule
    for r in suggest_rules(t):
        if produce(r, t) -> t_new succeeds: add t_new, break
        else: mark r applied to t
    if no rule produced: level(t) += 1
```

## Применение правила к терму

Шаги внутри `Solver::produce`:

1. **Перебор гипотез.** `HypothesisIterator` обходит подстановки
   параметров правила, обращающие шаблон в подтерм `t`. Каждая
   подстановка применяется к выводу правила и его ограничениям —
   получается **гипотеза** `(ĥt, {cₘ})`.
2. **Конкретизация.** Если в гипотезе остались несвязанные параметры,
   они доназначаются `Hypothesis::ground()` (см. [hypothesis.md](hypothesis.md)).
3. **Исключение дубликатов.** Если результат уже встречается среди
   термов с тем же значением `GOAL`, переход к следующей подстановке.
4. **Обоснование.** Каждое ограничение `cₘ` обосновывается подзадачей
   `Prove(cₘ)`. Если обоснование не удалось — гипотеза отвергается,
   переход к следующей подстановке.
5. **Добавление терма.** Успешно обоснованный результат добавляется в
   `Solution` со следующими метаданными: `level = 0`, пустой
   `applied_rules`, в `blocked_rules` копируются правила из атрибута
   `block(...)` исходного правила, `inference = Rule {…}` с
   ссылкой на правило, использованную подстановку и решения подзадач
   обоснования.
6. **`replace`.** Если правило имеет атрибут `replace`, исходный терм
   `t` помечается `REPLACED` и исключается из активных.

Подробности — `Solver::produce`, `Solver::try_prove_hypothesis`,
`HypothesisIterator`.

## Усмотрение ответа

Процедура `check_if_answer` определяет, является ли выбранный терм
ответом. Она зависит от типа целевой установки. Терм с флагом `GOAL`
(альтернативная цель) ответом сам по себе не считается.

Сначала проверяется специальный случай — терм-обёртка `answer(...)`:
если правило явно сформировало ответ через символ `answer`, обёртка
снимается, внутренний терм помечается ответом задачи. Это даёт
правилам способ задавать сложную логику усмотрения ответа на этапе
обучения.

### `find(x)` и `find(x, y, …)`

Терм `t` считается ответом, если он имеет вид `x == v` или `x in A`,
где `v` (или `A`) — известное (см. [terminology.md](terminology.md#известное-known))
выражение. Известность проверяется подзадачей `Prove(v is known)`.

Для multi-var `find(x, y, …)` целевые переменные связываются по мере
получения ответов: каждая успешно связанная переменная фиксируется в
`Solution::find_bindings`. Когда связаны все, ответ собирается как
конъюнкция: `x == … && y == … && …`.

Реализация: `Solver::check_find_answer`, `Solver::build_multi_find_answer`.

### `prove(s)`

Терм `t` считается ответом, если он синтаксически совпадает с целью
`s` (или с одним из термов с флагом `GOAL`, полученных
эквивалентными преобразованиями цели). Также ответом считается ситуация,
когда после нормализации сама цель свелась к тривиальной истине.

Реализация: `Solver::check_prove_answer`.

### `transform(s)`

В отличие от других типов задач, ранее усмотрение ответа для `Transform`
не производится во время цикла. Преобразование заключается в порождении
цепочки термов с флагом `GOAL` (через эквивалентные правила, применяемые
к цели). Когда уровень последнего активного goal-терма упирается в
`max_level`, ответом задачи помечается этот последний обоснованный
goal-терм.

Реализация: `Solver::check_transform_answer`.

## Преобразование цели и эквивалентные правила

Все три типа целевых установок допускают преобразование самой цели —
не только условий и выведенных утверждений. Для этого используются
правила с равносильным переходом (записывается `pattern <=> resolution`,
атрибут `Equivalence`).

Когда выбранный терм имеет флаг `GOAL`:

- К нему применяются только правила с `Equivalence` (для `prove`/`find`).
  Реализация: фильтрация в `Solver::suggest_rules`.
- В качестве «вспомогательной цели» при подборе правил используется
  не само `Goal`, а обёртка `prove(t)` — это позволяет правилам с
  `goal(prove(...))` срабатывать на промежуточных шагах преобразования
  цели задачи `find`/`prove`.
- Результат применения правила к goal-терму получает флаг `GOAL`,
  расширяя цепочку альтернативных целей.

В задачах `prove(s)` это даёт множество эквивалентов `s`, против
которых сравнивается каждый выводимый терм. В задачах `transform(s)`
именно цепочка goal-термов и есть процесс решения — её последний
элемент становится ответом.

## Завершение цикла

Цикл завершается одним из следующих способов:

| Условие | Статус решения |
|---------|----------------|
| Найден ответ | `Answer(idx)` |
| Превышен лимит итераций (`EXECUTION_DEADLINE_DEFAULT`) | `Err(ExecutionDeadline)` |
| Некого выбрать (нет активных термов с `is_proven`) | `Err(NoConditions)` |
| Уровень минимального активного терма превысил `max_level + 1` | `Err(NoSolutionsFound)` |
| Превышен лимит вложенности подзадач | `Err(MaxSubtaskLevelExceed)` |
| Получен сигнал отмены через `Tracer` | `Err(Canceled)` |

Дополнительно: для целевой установки `Transform` при завершении без
явного ответа в `check_transform_answer` выбирается последний
обоснованный goal-терм; он становится ответом задачи.

Реализация — `Solver::solve_impl`, статусы — `solver::task::solution::SolutionStatus`,
`SolveError`.

## Пошаговый пример

Возьмём задачу `find(x)` с условием `4x + 7 == 2x + 1`.
В системе пусть имеются два правила:

- `r₁` — перенос в левую часть: `a == b ⇒ a − b == 0`,
  ограничение `!symbolic_eq(b, 0)`, `Lᵣ₁ = 0`, атрибут `replace`.
- `r₂` — решение линейного уравнения: `a·u + b == 0 ⇒ u == −b/a`,
  ограничения `a != 0`, `b is known`, `Lᵣ₂ = 1`.

Начальное состояние: `t₁: 4x+7 == 2x+1` (`Lₜ = 0`),
`t₂: x` (`Lₜ = 0`, флаг `GOAL`).

| Шаг | Терм | Действие |
|-----|------|----------|
| 0 | `t₁`, `Lₜ = 0` | Подзадача `Transform(t₁)` ничего не нашла → `SIMPLIFIED`. Не ответ. Применяется `r₁`. Гипотеза `(4x+7) − (2x+1) == 0` → нормализация → `t₃: 2x+6 == 0`, `Lₜ = 0`. У `r₁` атрибут `replace` → `t₁` получает `REPLACED`. |
| 1 | `t₂`, `Lₜ = 0` | Не упрощается, не ответ, правил не подобралось → `Lₜ = 1`. |
| 2 | `t₃`, `Lₜ = 0` | Не упрощается. Не ответ. `r₁` пытается применить с подстановкой `{a→2x+6, b→0}`, но новый терм после нормализации совпадает с `t₃` → дубликат. Других правил уровня 0 нет → `Lₜ = 1`. |
| 3 | `t₂`, `Lₜ = 1` | Правил нет → `Lₜ = 2`. |
| 4 | `t₃`, `Lₜ = 1` | `r₂` пробует подстановку `{a→x, b→6, u→2}` — требует доказать `x != 0`, не получается → откат. Подстановка `{a→2, b→6, u→x}`: `x == −6/2` → нормализация → `x == −3`. Ограничения тривиальны. Добавляется `t₄: x == −3`, `Lₜ = 0`. |
| 5 | `t₄`, `Lₜ = 0` | Усмотрение ответа: терм имеет вид `x == v`, где `v = −3` известно. **Ответ найден.** |
